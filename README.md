# SAFE-ORCH

현장 작업 일정에 충돌이 생기면 AI Agent가 풀어서 안을 내고, 사람은 그 가운데 고르고 승인한다.
데모 현장은 조선소의 원·하청 혼재작업이다: 여러 업체의 작업이 같은 구역과 장비를 나눠 쓴다.

## 원칙

- **서버는 경계만 맡는다.** 사람의 권한, 안전 검사, 계산(충돌 찾기, 배치 풀이, 검증, 숫자)이다.
  무엇을 먼저 할지 같은 순서는 서버가 정하지 않는다.
- **판단은 Agent가 한다.** 모호한 문장은 스스로 해석하고 사람에게 되묻지 않는다.
  해석한 값은 사람이 화면에서 보고 고친다.
- **사람만 하는 것이 있다.** 작업 고정·해제, 안 고르기, 승인, 협의 항목 수용, 사실 수정 확인,
  Hold 해제, 자기 작업의 직접 이동. Agent에게는 이 도구가 없다.

## Agent

메인이 사건을 받아 전문 Agent를 부르고, 전문 Agent는 결과를 메인에게 돌려준다.
전문 Agent끼리는 서로 부르지 않는다. 작업 접수만 메인을 거치지 않는 입구다.

| Agent | 판단하는 것 |
|---|---|
| 메인 | 사건을 보고 어느 Agent를 부를지, 언제 사람을 기다릴지, 언제 끝내거나 이관할지 |
| 작업 접수 | 자연어 요청 문장에서 작업 값을 읽고, 문장에 없는 값은 스스로 정한다 |
| 일정 검토 | 들어온 일정의 충돌을 어떻게 묶어 볼지 정하고 검토 의견을 쓴다 |
| 재계획 | 충돌을 푸는 안을 만든다. 사람이 남긴 사유를 조건으로 바꿔 다시 푼다 |
| 협의 | 안이 바꾸는 작업의 담당자에게 확인을 받고, 확정된 계획을 알린다 |
| 신고 대응 | 지연 신고가 어느 작업의 무엇을 바꾸는지 해석해 사실 수정안을 낸다 |

## 흐름

### 일정 넣기

```
일정 넣기
  → 메인
  → 일정 검토: 충돌을 묶음으로 정리하고 의견을 쓴다
  → 재계획 × 3: 기존 위주 · 추가 위주 · 적절하게
  → Supervisor가 안 비교에서 [이 안 고르기]
  → 협의: 담당자마다 변경 요청 한 통, 받은 요청에서 항목별 수락·이견
  → 모두 답하면 Supervisor가 [승인·확정]
  → 협의가 확정 통지를 보낸다
```

- 세 방향은 무엇을 지킬지가 다르다. 기존 위주는 이미 계획된 작업을, 추가 위주는 들어온 작업을
  문서 자리에 두려 하고, 적절하게는 바뀌는 작업 수 전체를 줄인다.
- 담당자가 이견을 내면 메인이 세 방향을 다시 부른다. 재계획은 이견의 사유를 시각·자원 조건으로
  바꿔 다시 풀고, 새 안이 다시 안 비교에 오른다.
- 답이 오지 않는 항목은 Supervisor가 사유를 적어 수용할 수 있다. 승인과 수용은 고른 안에만 된다.

### 자연어 요청

```
자연어 요청
  → 작업 접수: 묻지 않고 해석해 작업을 만든다
  → 메인
  → 재계획: 한 번
  → Supervisor가 [이 안 고르기]
  → 협의
  → [승인·확정]
  → 통지
```

- 작업 접수가 스스로 정한 값은 작업 카드에 "정함"으로 표시되고, 요청자가 카드에서 고친다.
- 재계획을 다시 부르는 것은 안을 받지 못했을 때와 거절·이견이 나왔을 때다.
- 충돌이 없으면 재계획 없이 재확인 안이 바로 올라온다.

### 지연 신고

```
지연 신고
  → Hold: 신고가 접수되는 순간 서버가 건다. 걸려 있는 동안 승인이 막힌다
  → 메인
  → 신고 대응: 대상 작업을 해석하고, 영향 분석을 한 뒤 사실 수정안을 낸다
  → Supervisor가 받은 요청에서 사실 수정 확인
  → Supervisor가 Hold 해제
  → 재검사: 충돌이 있으면 재계획, 없으면 재확인 안
```

- 영향 분석은 새 값이 지금 계획된 시작보다 몇 분 뒤인지를 보여 준다. "10분 지연"은 계획된
  시작에서 센다.
- 사실 수정안은 Supervisor가 확인해야 효력이 생긴다.

## 안을 고르는 근거

- **숫자는 서버가 계산한다.** 안마다 기존 작업 변경 수, 추가 작업 변경 수, 기준에서 옮긴 거리가
  안 비교에 보인다. 시간 한도 안에 최적이 확인되지 않은 안은 "최적 미확인"으로 표시된다.
- **Agent의 글은 의견이다.** 일정 검토 의견과 재계획이 적은 이유는 서버 숫자와 구분해 따로 보인다.
  글은 고르기와 승인에 아무 효력이 없다.
- **고르는 것은 사람이다.** Agent는 안을 숨기거나 빼지 않는다.

## 실행

필요한 것: Python 3.12와 [uv](https://docs.astral.sh/uv/), Node.js와 npm, OpenAI API 키.

**설정.** 저장소 루트의 `.env.example`을 `.env`로 복사하고 `OPENAI_API_KEY`와 `OPENAI_MODEL`을 채운다.
시연에 쓴 값은 `OPENAI_MODEL=gpt-6-luna`, `OPENAI_REASONING_EFFORT=none`이다.
현장의 지금은 `SITE_NOW`(`.env.example` 값 그대로 `2026-10-12T09:00+09:00`)로 고정돼 있다.

**처음 한 번 DB 만들기.** 서버를 끈 상태에서 한다. 확인 문구로 `RESET safe_orch`를 입력한다.

```
cd backend
uv run python -m scripts.reset_db
```

Pack(`domain_packs/shipyard`)이 바뀌면 서버가 뜨지 않으므로 다시 reset한다.

**서버.**

```
cd backend
uv run uvicorn app.main:app --port 8000
```

**화면.** 브라우저에서 http://localhost:5173 을 연다(`/api`는 8000으로 프록시된다).

```
cd frontend
npm install
npm run dev
```

**검증(API 키 없이).**

```
cd backend
uv run pytest
uv run ruff check

cd frontend
npm run lint
npm run build
```

**시연해 보기.** 사용자는 화면 위의 Actor에서 바꾼다.

- Planner A로 [일정 넣기] 탭에 `domain_packs/shipyard/schedules/schedule_YARD-01_UA_test.json`을 넣는다.
- 그 Case가 승인된 뒤 Planner B로 `schedule_YARD-01_UB_test.json`을 넣는다.
- 자연어 요청과 지연 신고는 각 탭의 [시연: …] 버튼으로 채워 넣는다. [이 안 고르기]와 [승인·확정]은 Supervisor로 한다.
