# 기존 자산 지도

새 기능을 만들기 전에 여기서 먼저 찾는다. 내용은 옮겨 적지 않고 위치만 가리킨다. 경로는 저장소 루트 기준.

## 1. 실행·설정
- 설정 클래스: `backend/app/config.py` `Settings`·`get_settings()`(캐시). 저장소 루트 `.env`를 읽는다. 예시는 `.env.example`.
- 환경 변수(모두 `Settings` 필드):
  - `DB_PATH` — SQLite 파일 경로(상대면 저장소 루트 기준).
  - `OPENAI_API_KEY`·`OPENAI_MODEL` — 실제 모델 호출용.
  - `OPENAI_TEMPERATURE`·`OPENAI_SEED`·`OPENAI_REASONING_EFFORT` — 값이 있을 때만 모델에 넘긴다(`agents/llm.py` `model_settings`).
  - `DEMO_MODE` — `/api/dev/*` 사용 여부(`api/dev.py`).
  - `PACK` — `domain_packs/<pack>/` 선택.
  - `DISPATCH_WORKER`·`DISPATCH_POLL_S` — 기동 시 워커 스레드 시작 여부·폴링 간격(`main.py` `lifespan`).
  - `MAIN_AUTO_START` — 사건 → 메인 자동 시작(`store/repos/cases.py` `deliver_event`에서 읽음). 끄면 사건은 기록만 된다.
  - `MAIN_MAX_STEPS`·`MAIN_MAX_AGENT_CALLS` — 메인 Budget의 기본값(`agents/specs/main.py`가 기동 때 읽음). 실제 한도는 사람이 만든 일만큼 늘어난다(AG-30): 한 바퀴분 `ROUND_STEPS`·`ROUND_AGENT_CALLS`, 상한 `MAX_EXTRA_ROUNDS`, 계산 `budget_limits`(같은 파일). 사람이 만든 일 세기와 Run별 한도는 `agents/casefacts.py` `human_work`·`budget_limits`, 화면에는 Run 요약의 `budget_max`.
  - `SITE_NOW` — 현장의 지금을 고정(ISO 8601, 오프셋 필수). 비면 실제 시계. 읽는 곳은 `app/clock.py` `site_now` 하나.
  - `LANGSMITH_TRACING` — `Settings` 필드가 아니다. `tests/conftest.py`가 환경변수로 false를 강제하고, 예시는 `.env.example`.
- 실행: `cd backend && uv run uvicorn app.main:app --reload --port 8000` / `cd frontend && npm run dev`(`/api`는 `vite.config.ts`가 8000으로 넘김).
- 테스트·검사: `cd backend && uv run pytest` / `cd frontend && npm run lint`·`npm run build`(`frontend/package.json`).
- DB 초기화는 사람이 한다. 서버는 버전이 다르면 기동을 멈추고 자동 초기화하지 않는다(`store/db.py` `init_db`).
  - 명령줄: `cd backend && uv run python -m scripts.reset_db` — 확인 문구 입력 필요(`backend/scripts/reset_db.py`).
  - 화면·API: `POST /api/dev/reset`(`api/dev.py` `post_reset`, `db.rebuild_schema` + `seed_pack`).

## 2. 모듈 지도 (`backend/app/`)
- `config.py` — 설정. `main.py` — 앱 조립, 기동 검사(스키마·Pack 일치), 워커 시작, 오류 응답 모양.
- `domain/` — 순수 모델·계산(hash, 근무 달력, 자원 적격성, Consultation 상태, ID). app 내부를 import하지 않는다.
- `packs/` — Domain Pack YAML 읽기·검증(`LoadedPack`).
- `store/` — SQLite 연결·트랜잭션(`db.py`), 스키마(`schema.sql`), 테이블별 조회·쓰기(`repos/`).
- `rules/` — 충돌 탐지(`engine.py` `detect_conflicts`). `solver/` — SearchSpec 생성·CP-SAT 계산·후보 생성.
- `validator/` — 후보 검증(`validator.py` `validate`).
- `commands/` — 사람 명령(작업 요청·접수·승인·거절·WAIVE·신고·Hold 해제·답변·제안 확인·Run 취소·작업 고정·고정 해제·희망 영역·안 고르기·직접 이동·작업 없애기·작업 값 고치기). 공통 실행은 `service.py`.
- `coordinator/` — 후속 작업 처리: `dispatcher.py`(워커·`process_next`·`run_until_idle`, 기동 복구 `recover_on_startup`), `transitions.py`(job 종류별 핸들러 `HANDLERS`·`start_run`·`resume_run`·`continue_run`, RUNNING으로 남은 Run에 CONTINUE_RUN을 등록하는 `recover_running_runs`).
- `agents/` — Agent 실행 계층(5절). `api/` — HTTP 라우터: `commands.py`(명령), `state.py`(상태·Run 조회), `meta.py`(Pack 표시 정보), `dev.py`(시연값·reset), `health.py`, `deps.py`(공통).
- import 경계 검사: `backend/tests/test_architecture.py`(금지 import, registry·executor 호출 위치, Gateway 권한 함수 없음, 금지 LangGraph 기능).

## 3. 저장소
- 스키마: `backend/app/store/schema.sql`. 버전: `store/db.py` `SCHEMA_VERSION`(DB에는 `schema_meta` 테이블). 스키마 테스트: `tests/test_schema.py`.
- 트랜잭션 도우미(`store/db.py`): `write()`(쓰기), `read()`(읽기 연결), `read_tx()`(여러 조회를 한 시점으로), `connect()`·`close()`. 오류: `NestedTransactionError`·`StoreBusyError`·`SchemaVersionMismatchError`.
- 조회 결과 dict 변환·JSON 컬럼 읽기·쓰기: `store/repos/_rows.py` `rows`·`dumps`·`loads`.
- 테이블 (불변 = UPDATE·DELETE 트리거로 금지, 전이 제한 = 정해진 상태 전이만·삭제 금지, 표시 없음 = 트리거 없음):
  - `schema_meta` — 스키마 버전.
  - `site` — 현장 1개와 `context_version`·`plan_revision`. 증가는 `repos/site.py` `bump_*`.
  - `work_unit`·`actor`·`zone`·`zone_relation`·`resource` — Pack에서 seed한 현장 사실(`repos/seed.py`, 조회는 `repos/site.py`·`repos/resources.py`). `resource`에는 표시 이름·사용 가능 구역(`allowed_zone_ids`)·속성 값(`attributes`)·시간당 비용·메모가 있다.
  - `pool` — 수량 풀(종류·소유 Unit·허용 Unit·수량·단가). Pack에서 seed하고 조회는 `repos/resources.py` `list_pools`. Snapshot에는 `pools`로 들어간다.
  - `task` — 작업. 수정은 새 revision INSERT(`repos/tasks.py`). `fields`의 기록마다 값별 출처 `origins`(Agent가 정한 값만 적힌다). lifecycle에 CANCELLED(담당자가 없앤 계획 작업). `resource_requirements`·`pool_demands`는 작업 값만 담고, 작업 유형 기본값은 조회 때 Pack에서 도출한다.
  - `snapshot` — 계산 시점의 사실 묶음. 불변(`repos/snapshots.py`, `repos/records.py`).
  - `search_spec` — Solver 탐색 범위와 Agent가 건 조건(`conditions`)·목적 순서(`objective`). 불변(`repos/records.py`).
  - `solver_result` — Solver 단계별 결과. 불변(`repos/records.py`).
  - `candidate` — 계획 후보. 종류 REPLAN·RECONFIRM·MOVE(직접 이동)·REMOVE(작업 없애기), 사람이 만든 후보는 그 사람 `made_by`. 불변(`repos/records.py`).
  - `validation` — 후보 검증 결과. 불변(`repos/records.py`).
  - `audit` — 적용된 명령 기록. 불변(`repos/commands.py`).
  - `plan` — 확정 계획 revision(`repos/plans.py`).
  - `command_result` — 멱등 키별 명령 결과. 불변(`repos/commands.py`).
  - `decision` — 승인·거절·WAIVE·안 고르기(`CHOOSE`). 불변(`repos/decisions.py`).
  - `task_pin` — 사람이 건 작업 고정(누가·언제 걸고 풀었는지). 전이 제한 ACTIVE → RELEASED, 작업당 ACTIVE 하나(`repos/pins.py`). Snapshot에는 `pins`로 들어간다.
  - `preferred_window` — 담당자가 그린 희망 영역(작업당 시각 구간 하나). 전이 제한 ACTIVE → CLEARED(`repos/pins.py`). Snapshot에 넣지 않는다.
  - `event` — 현장 신고. 불변(`repos/events.py`).
  - `case_event` — 메인에게 갈 사건(작업 준비됨·신고·Hold 해제·후보 승인·거절·하위 Run 종료·요청 철회·작업 고정 `TASK_PINNED`·고정 해제 `TASK_UNPINNED`·안 고르기 `CANDIDATE_CHOSEN`·직접 이동 `TASK_MOVED`·작업 없애기 `TASK_REMOVED`·카드에서 값 고치기 `TASK_EDITED`). 순번·종류·참조·Case·`dedupe_key`. 불변, 처리 상태 칸 없음(`repos/case_events.py`).
  - `hold` — 신고로 걸린 보류. 전이 제한(`repos/events.py`).
  - `consent` — 담당자 사전 동의 범위. 불변(`repos/consents.py`).
  - `consultation` — 후보별 협의 항목. 불변(`repos/consultations.py`).
  - `dispatch_job` — 후속 작업 대기열(`repos/dispatch.py`). 종류 START_RUN·RESUME_RUN·CONTINUE_RUN(기동 복구)·VALIDATE·BUILD_CONSULTATION·RECHECK.
  - `agent_run` — Agent Run과 Budget 사용량. 전이 제한(`repos/runs.py`). agent_type에 MAIN, 상태에 BLOCKED, 부모 Run `parent_run_id`, 대기 종류 CHILD_RUN·HUMAN_DECISION, 전문 Agent 호출 수 `agent_calls_used`, 마지막으로 본 사건 순번 `last_event_seq`. 열린 MAIN은 site당 하나·열린 하위 Run은 부모당 하나(부분 유일 인덱스).
  - `agent_step` — step 기록(관찰·Action·Guard). 전이 제한(`repos/runs.py`).
  - `solver_job` — Solver step 예약·등록. 해가 기존 후보와 같은 배치였으면 `same_candidate_id`. 전이 제한(`repos/runs.py`).
  - `proposal` — 사람 확인을 기다리는 제안. 전이 제한(`repos/messages.py`).
  - `message` — 사람에게 보낸 질문·요청·통지와 답. 전이 제한(`repos/messages.py`). 서버가 Run 없이 보낸 통지(직접 이동)는 `run_id`·`step_no`가 비어 있다.
- Pack과 DB 일치 검사: `repos/site.py` `ensure_pack_matches`.

## 4. 이미 있는 공용 도우미 (새로 만들기 전에 찾아볼 것)
- 직렬화·hash: `domain/canonical.py` `canonical_json`·`sha256_hex`·`canonical_hash`. 객체별 hash는 `domain/hashes.py`(`search_spec_hash`·`search_key`·`candidate_hash`), 변경 hash는 `domain/consultation.py` `change_hash`, Pack hash는 `packs/loader.py` `compute_pack_hash`.
- ID 생성: `domain/ids.py` `new_id`.
- 도메인 모델: `domain/models.py`(`Frozen` 기반. Task·Assignment·Plan·Snapshot·Candidate·Validation·AgentRun 등).
- 자원 적격성 판정(유형·권한·가용 구간 없음·구역·요구 조건): `domain/eligibility.py` `exclusion_reasons`(Rule Engine·Solver 필터·실행 검사·조회·폼이 같이 쓴다), 작업이 아닌 값의 입력 모양 `ResourceNeed`, 조건 하나 `meets`, 요구 조건과 속성 선언 대조 `requirement_error`, 모든 구역 표시 `ALL_ZONES`. 테스트는 `tests/test_eligibility.py`.
- 자원 속성·요구 조건 모델: `domain/models.py` `ResourceAttribute`·`Requirement`, 작업의 조건 전체는 `Task.requirements`(작업 유형 기본값 `default_requirements` + 작업 값 `resource_requirements`).
- 수량 풀·수요 모델: `domain/models.py` `PoolKind`·`Pool`·`Demand`·`PoolDemand`, 그 Unit이 그 종류에 쓰는 풀 `pool_for`, 작업의 종류별 수요 `Task.demands`(기본값 `default_demands`와 작업 값 `pool_demands` 중 큰 쪽)·필수 직종 `Task.required_kinds`, 풀 초과 내용 `PoolExcess`(`Conflict.pool`).
- 누적 제약(겹치는 작업의 수요 합 ≤ 풀 수량): 탐지는 `rules/engine.py` `_pools`(`POOL_CAPACITY`·`POOL_MISSING`), Solver는 `solver/cpsat.py` `_build`의 풀별 `add_cumulative`. 테스트는 `tests/test_pools.py`.
- 근무 달력: `domain/calendar.py`(`fits_work_interval`·`start_domain`·`has_work_slot`·`work_minutes`·`work_delay`·`local_clock`).
- 현장의 지금: 읽기는 `clock.py` `site_now`(분 단위 UTC, 판정·계산에 쓰지 않음), 관찰용 표현은 `domain/calendar.py` `now_view`(Intake·Event Response 관찰의 `site_now`).
- 명령 공통 실행(멱등·권한 문맥·Audit·거절 시 되돌림): `commands/service.py` `run_command`, `Body`·`Result`·`CommandContext`·`CommandOutcome`·`request_hash`.
- Case·Run 수명(`store/repos/cases.py`): 사건 전달과 메인 시작 `deliver_event`·`open_main`, 열린 메인이 있을 때만 전달 `deliver_to_open_main`(고정·해제), 깨우기 `wake_run`, 재개 claim `claim_resume`, 종료 `end_case_run`(하위 Run 종료 사건·메인 깨우기·메인 종료 때 하위 Run 정리·종료 통지)·`end_candidate_runs`·`stale_active_runs`, 보낸 요청 정리 `cancel_requests`, 대기열 `queued_task_ids`·`promote_queued`, 재검사 등록 `register_recheck`·`recheck_key`, `supervisor_actor`, 서버 문구 `intake_incomplete_text`·`main_ended_text`.
- 전문 Agent 호출의 키와 사실 지문(`store/repos/calls.py`): `call_key`(사전 확인은 need ID 목록)·`fingerprint`·`last_result`. 하위 Run이 끝날 때의 지문은 `CHILD_RUN_ENDED` 사건 ref에 있다.
- 충돌 그룹(공유 작업으로 묶은 최소 계산): 순수 계산 `domain/groups.py` `conflict_groups`·`group_id`·`ConflictGroup`, 그 Unit의 움직일 수 있는(고정되지 않은) 작업 `movable_task_ids`.
- 작업 고정·희망 영역(AG-27): 명령 `commands/pins.py` `pin_task`·`unpin_task`·`set_preferred_window`·`clear_preferred_window_command`, API `POST /tasks/{id}/pin`·`/unpin`·`/preferred-window`·`/preferred-window/clear`, 저장·조회 `store/repos/pins.py` `list_active_pins`·`active_pin_views`·`preferred_windows`, 모델 `domain/models.py` `Pin`·`TaskMovable`. 고정된 작업은 `solver/search_spec.py`가 축을 닫고 `validator/validator.py` C06이 `TASK_PINNED`로 검사한다. 화면은 `Timeline.tsx`.
- 직접 이동(AG-31·CV-28): 명령 `commands/moves.py` `move_task`(API `POST /tasks/{id}/move`), 읽기 전용 `move_range`(놓을 수 있는 시작 구간, `GET /tasks/{id}/move-range`)·`move_check`(놓은 자리 판정, `GET /tasks/{id}/move-check`), 셋이 같이 쓰는 판정 `_judge`·`_verdict`, 맞춤 단위 `SNAP_MIN`, 통지 문구 `move_notice_text`. 작업 없애기는 같은 파일의 `remove_task`(API `POST /tasks/{id}/remove`), 읽기 전용 확인 `remove_check`(`GET /tasks/{id}/remove-check`, 계획 밖 요청이면 철회 경로 `WITHDRAW`), 같이 쓰는 판정 `_remove_verdict`, 통지 문구 `remove_notice_text`. 둘이 같이 쓰는 확정·통지는 `_commit`·`_notify_linked`. MOVE·REMOVE 후보의 규칙은 `validator/validator.py` C02·C06. 화면은 `Timeline.tsx` `startMove`·`askRemove`와 `api.ts` `fetchMoveRange`·`fetchMoveCheck`·`fetchRemoveCheck`. 테스트는 `tests/test_moves.py`.
- 메인이 보는 Case 사실(`agents/casefacts.py`): `build`(그룹별 Unit·움직일 수 있는 작업·미시도 범위·이전 결과의 길과 openers, Hold, 후보·검증·협의·통지, 하위 Run 결과, 이 Case의 열린 일, 지금 받아들여지는 호출, 사전 확인으로 물을 수 있는 need), `current_groups`·`primary_for`·`acting_actor`, 통지 대상 `notice_targets`·`notified_actors`, 서버가 만드는 결과 `run_result`, 거절 사실 `rejection_facts`, 재호출 판정 `same_facts`.
- Run·step 기록(`store/repos/runs.py`): `insert_run`·`reserve_step`·`complete_step`·`abort_step`·`charge`·`enter_wait`·`end_run`·`abort_reserved`·`mark_restart`(기동 복구)·`has_open_case`·`list_active_runs`, 이 Case에서 해 본 탐색 `tried_search_keys`(무효가 된 후보의 탐색은 미시도)·`list_attempts`, 상수 `ACTIVE`·`CASE_AGENT_TYPES`.
- 사건 기록(`store/repos/case_events.py`): `record_case_event`(dedupe 키, Case는 주어진 값 → 열린 Case → 새 Case)·`case_of`·`open_case_id`·`list_case_events`, 종류 `KINDS`. 사건이 생기는 트랜잭션에서 부른다.
- 후속 작업 대기열(`store/repos/dispatch.py`): `register_job`(dedupe 키)·`claim_next`·`mark_done`·`mark_failed_attempt`·`requeue_claimed`.
- 메시지·제안(`store/repos/messages.py`): `insert_proposal`·`insert_message`·`set_message_reply`·`decide_proposal`·`list_inbox`·`list_change_requests`·`change_answers`·`list_fact_updates`, 사전 확인의 질문과 답 `list_owner_asks`·`open_owner_asks`, 담당자가 거절한 값(작업 revision 기준, 현장 전체) `declined_values`.
- Snapshot: `store/repos/snapshots.py` `build_snapshot_content`(읽기만)·`create_snapshot`(저장).
