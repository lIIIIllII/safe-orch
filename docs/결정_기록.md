# SAFE-ORCH 결정 기록

2026-10-03. 되돌려질 위험이 있는 결정만 적는다. 다른 선택지가 그럴듯했고, 이유를 모르면 누군가 "고치려" 할 결정이다.

- 항목 하나 = 결정 한 줄 + 이유 한 줄. 코드·SQL·함수 이름은 쓰지 않는다.
- 구현 기록("~를 구현했다")은 커밋 메시지에 둔다.
- 결정이 바뀌면 그 항목을 고쳐 쓰고, 무의미해지면 지운다. 옛 내용은 git에 있다. 지운 번호는 다시 쓰지 않는다.
- 200줄을 넘기지 않는다. 넘으면 비슷한 항목을 합친다.
- 단계를 닫을 때마다 한 번 정리한다(합치기·무의미해진 항목 지우기).

## Agent (AG)

- **AG-01** 순서 규칙("무엇을 한 뒤에만 무엇")은 서버가 아니라 스킬 지침에 둔다. 서버는 권한·안전·동의·인자 유효성·Budget만 강제한다.
  이유: 서버가 순서를 쥐면 매 step 선택지가 "다음 하나 vs 이관"뿐이라 Agent가 스크립트가 된다. 지침이 지켜지지 않으면 지침 문구·관찰 사실·도구 모양으로 고치고, 서버 순서 규칙으로 되돌리지 않는다. 서버에 남는 흐름 규칙은 같은 요청 두 번 금지류뿐이며 나머지 둘(확인 대기 중 조회·분석 닫힘, 미시도 범위)은 뒤 단계에서 다시 본다.
- **AG-02** 스킬은 행동마다 선언하고(켜 둔 상태를 저장하지 않는다) 사실 조건으로만 열리며, 쓸 수 있는 도구는 열린 스킬의 도구 ∩ Agent 허용 도구다. 유효한 인자 값이 하나도 없는 도구는 뺀다(순서가 아니라 유효성).
  이유: 켜 둔 상태 방식은 스킬만 바꾸는 step이 생겨 Budget이 실제 행동만 세지 못하고, 순서 조건을 두면 AG-01의 문제가 스킬 이름으로 다시 생기며, 여러 Agent가 공유하는 스킬이 Agent 권한을 넓히면 안 된다(예: Replanning은 사람 도구를 쓰지 못한다).
- **AG-05** Agent 호출은 Coordinator가 하위 Run을 만들고 부른 쪽은 대기·재개하는 방식으로 한다. LangGraph subgraph로 직접 부르지 않는다.
  이유: checkpointer 없이는 하위 Agent가 사람 답을 기다리는 동안 상위 그래프 상태를 보존할 수 없다.
- **AG-06** 전문 Agent는 다른 Agent를 부르지 않고 사람에게 이관하지도 않는다. 막히면 이유와 필요한 것을 메인에게 돌려준다.
  이유: 호출이 거미줄이 되면 핑퐁·순환을 막기 어렵고 판단이 흩어진다. 다음에 누구를 부를지는 메인 한곳에서 판단한다.
- **AG-07** 메인은 한 번에 하나이고 일이 남아 있는 동안만 산다. 새 사건은 열린 메인을 깨운다.
  이유: 사건마다 메인을 띄우면 겹친 사건의 순서를 판단할 곳이 없고, 상주 메인은 관찰·Budget이 끝없이 쌓이며 하나가 죽으면 현장이 멈춘다.
- **AG-08** 메인 Budget 상한에 닿으면 새 사건을 받지 않고 지금 일만 정리한 뒤, 남은 사건을 다음 메인에게 넘긴다.
  이유: 이관하면 사건이 버려진다. 넘겨주기는 수명을 끊으면서 사건을 잃지 않는다.
- **AG-09** 작업 담당자 확인은 Coordination 한 창구로만 한다. 요청자·신고자와의 대화는 Intake·Event Response가 직접 한다.
  이유: 여러 Agent가 같은 담당자에게 따로 묻는 것을 막고, 여러 그룹의 질문을 한 번에 묶는다.
- **AG-10** AI는 일정·점수·중요도를 직접 계산하지 않는다. 설명과 추천은 서버 지표를 가리킨다.
  이유: 재현·검증이 안 되고, 모델에 따라 결과가 달라진다.
- **AG-11** Agent 지침 원문은 코드에 두고 바뀌면 prompt 버전을 올리며(fingerprint 테스트), 모델에 준 관찰과 AgentStep에 저장하는 관찰은 같다.
  이유: 모델이 실제로 받은 문장과 본 관찰이 기록과 같아야 AgentStep에 남은 버전으로 판단을 재현하고 심사·평가 증거로 쓴다.
- **AG-13** 모든 Action은 실행 직전에 관찰 이후 버전이 바뀌었는지 확인하고, 바뀌었으면 실행하지 않는다.
  이유: 옛 관찰로 고른 행동을 새 사실 위에서 실행하지 않는다. "해가 없다"는 이관도 사실 판단이다.
- **AG-14** 제안(사실 수정·제약 초안)을 낸 Agent는 사람이 확인할 때까지 Run을 끝내지 않는다.
  이유: Run이 끝나면 그 Run이 보낸 요청이 정리되어 제안이 무효가 된다.
- **AG-15** Event Response 관찰에는 자기가 보낸 질문 문장을 넣지 않는다. Intake에는 넣는다.
  이유: 넣었더니 답이 안 온 항목을 같은 질문으로 반복해 live run이 0/3이 됐다. Intake는 값 확인이라는 다음 수단이 있어 오히려 좋아졌다.
- **AG-16** 신고 접수가 열린 Run을 무효로 만들 때 Intake Run은 뺀다.
  이유: 작성 중인 접수 값은 아직 사실이 아니고, 완료할 때 다시 검증한다.
- **AG-17** LLM 전송 재시도는 SDK에 맡기지 않고 직접 1회 하며 시도 수를 Budget에 센다. 크레딧 부족은 재시도하지 않고 설정 오류로 끝낸다.
  이유: SDK 안의 재시도는 밖에서 보이지 않아 Budget에 셀 수 없다. 크레딧 부족은 기다려도 풀리지 않는다.
- **AG-19** 열리지 않은 스킬이나 스킬 밖 도구를 고른 행동은 거절하되 형식 오류 연속에 세지 않는다.
  이유: 스킬 선택 실수는 판단 실수라 Run을 끝낼 사유가 아니고 가드 거절로 기록된다(EV-02).
- **AG-20** 사람과 대화하는 스킬은 상대별로 나눈다(요청자·신고자·담당자).
  이유: 상대와 도구가 달라 공용 지침이 막연해지고, 지침이 그 도구가 없는 스킬에 붙는다.
- **AG-21** Agent 도구의 시각 인자는 현장 날짜·시각 문자열이고 서버가 분으로 바꾼다.
  이유: 모델이 날짜를 분으로 바꾸다 틀리고(셋째 날을 둘째 날로), AI는 일정을 계산하지 않는다(AG-10).

## 저장소·실행 (ST)

- **ST-01** 업무 상태와 Agent 실행 상태의 기준은 SQLite 하나다. LangGraph checkpointer·interrupt를 쓰지 않는다.
  이유: 실행 상태를 따로 두면 두 저장소의 정합 규칙이 필요하다. 매 step 최신 상태를 다시 관찰하므로 같은 Run을 처음부터 다시 호출하면 된다.
- **ST-02** 트랜잭션은 중첩하지 않고 하위 함수에는 트랜잭션을 인자로 넘기며, 트랜잭션 안에서 LLM·Solver·파일 I/O·await를 하지 않는다.
  이유: 중첩하면 커밋·롤백 범위가 흐려져 부분 반영이 생기고, 쓰기 트랜잭션이 곧 site 잠금이라 오래 잡으면 모든 명령이 기다리다 timeout난다.
- **ST-04** 거절된 명령은 handler의 쓰기를 모두 되돌린 뒤 결과 기록만 남긴다.
  이유: "거절이면 도메인 변화 없음"을 코드 습관이 아니라 구조로 보장한다.
- **ST-05** 후보·검증·협의의 상태(STALE, 표시 상태)는 저장하지 않고 조회할 때 계산한다.
  이유: 불변 기록과 표시가 어긋나지 않는다.
- **ST-06** 메시지 취소와 제안 무효는 계산하지 않고 저장한다.
  이유: 늦은 답 기록과 받은 요청 화면에 확정된 상태가 필요하다.
- **ST-07** 불변 기록(스냅샷·탐색 조건·Solver 결과·후보·검증·결정·감사)은 DB 트리거로 수정·삭제를 막는다.
  이유: 판단 근거가 나중에 바뀌면 감사 증거가 되지 못한다.
- **ST-08** 스키마 마이그레이션, 자동 초기화, 빈 DB 자동 seed를 하지 않는다. 버전이 다르면 기동을 멈추고, 초기화는 확인 문구를 거친 reset으로만 한다.
  이유: 자동 초기화는 Hold·Plan 기록을 조용히 지운다.
- **ST-09** 같은 멱등 키는 같은 명령·본문에만 저장된 결과를 돌려준다. 잠금 timeout만 결과를 저장하지 않는다.
  이유: 응답을 못 받은 재시도가 효과를 두 번 내지 않게 하고, 다른 요청이 같은 키로 옛 결과를 받지 않게 한다.
- **ST-10** 작성 중인 자연어 접수 값은 작업이 아니라 Run 기록에 둔다. 작업은 확인이 끝날 때 처음 생긴다.
  이유: 미완성 값이 스냅샷·충돌·버전에 영향을 주면 안 된다.
- **ST-11** 버전은 site 하나가 아니라 범위(작업·자원·구역)별로 둔다. 후보는 자기가 건드리는 범위가 바뀔 때만 무효가 된다.
  이유: site 하나면 엮이지 않은 그룹의 확정이 다른 그룹의 후보·협의·사람 답을 모두 무효로 만든다.
- **ST-12** 그룹을 확정할 때 그 변경만 현재 계획에 합치고, 합친 전체를 다시 검증한다.
  이유: 엮임 계산이 연결 하나를 놓쳐도 낡은 사실 위의 후보가 통과하지 않게 한다.
- **ST-13** 첫 구현에서는 ACTIVE Hold가 하나라도 있으면 모든 승인을 막는다.
  이유: 관련 없는 Hold를 무시하는 것은 안전 판단 완화라 따로 근거가 있어야 한다.
- **ST-14** 테스트는 .env를 읽지 않고, 기준 설정(외부 모델 끔, Agent 자동 시작 끔)을 한곳에서 고정한다.
  이유: 개발자 .env 때문에 테스트 46개가 실패한 적이 있다. 기준을 끈 상태로 두어야 결정론 회귀가 유지된다.
- **ST-15** 담당자 답은 후보가 아니라 변경(작업 revision·전후 배정)에 묶고, Consent로 남기지 않는다.
  이유: Consent는 Context를 올려 방금 동의받은 후보를 무효로 만든다.
- **ST-16** 취소된 요청에 온 늦은 답은 같은 변경이 다시 나와도 인정하지 않는다.
  이유: 거둬들인 요청의 답을 살리면 Hold 중 결정을 허용하는 셈이다.
- **ST-17** 현장의 지금은 서버 한곳에서 읽고, 테스트·평가·live run은 고정한다.
  이유: 실제 시계는 결정론을 깬다.

## 계산·검증 (CV)

- **CV-01** Validator는 Solver 코드를 쓰지 않는다. Rule Engine은 같이 쓴다.
  이유: 같은 코드로 만들고 검사하면 같은 버그를 못 잡는다.
- **CV-02** Validator가 모르는 규칙은 무시하지 않고 실패로 본다.
  이유: Pack과 코드가 어긋난 무결성 문제를 조용히 통과시키지 않는다.
- **CV-03** Solver가 낸 후보가 규칙 검사에서 실패하면 Run을 오류로 멈춘다(입력 미확인만 걸리면 계속).
  이유: 모델과 검증이 어긋난 것이라 계속하면 같은 오류를 반복한다.
- **CV-04** 탐색에는 무결성 해시(스냅샷 포함)와 실효 탐색 키(Solver 입력만) 두 가지를 둔다. "이미 해 본 탐색"은 실효 탐색 키로 판정한다. 실효 탐색 키에는 Solver 입력이 모두 들어간다(구역·속성·요구 조건·풀·수요 포함).
  이유: 동의·버전 번호처럼 Solver 입력이 아닌 변화 때문에 같은 탐색이 새것처럼 보여 반복됐다.
- **CV-05** 실효 탐색 키에 확인된 제약을 직접 넣지 않는다. 제약은 탐색 축을 통해서만 반영된다.
  이유: 처음에 넣었더니 범위 밖 작업의 제약 때문에 같은 탐색이 다시 열려, 거절 뒤 L0를 또 풀었다.
- **CV-06** Solver Budget은 돌리기 전에 차감하고, 결과가 버려져도 돌려주지 않는다.
  이유: 결과를 모르는 호출도 사용한 것으로 센다. 돌려주면 STALE이 반복될 때 Budget 상한이 의미를 잃는다.
- **CV-07** CP-SAT는 worker 하나, 고정 seed로 돈다.
  이유: 같은 입력이면 같은 답이어야 재현·검증과 "이미 해 본 탐색" 결과 반환이 성립한다.
- **CV-08** Pack에는 자원 겹침(CAPACITY) 규칙이 정확히 하나 있어야 한다.
  이유: Solver는 Pack과 관계없이 자원 겹침을 막으므로 Validator 기준을 맞춘다. 없으면 겹치는 후보가 통과할 수 있었다.
- **CV-09** 선행 작업이 없는 작업은 건너뛰지 않고 막는다. 후속 요청이 있는 작업은 후속부터 철회해야 한다.
  이유: 조용히 건너뛰면 선후행을 어긴 계획이 통과한다.
- **CV-10** 근무 달력은 기본 제약이고 자원 가용 구간과 따로 둔다.
  이유: 장비 가용과 현장 근무는 다른 사실이고, 합치면 야간 배치가 두 번 보고된다.
- **CV-11** 위험 태그는 입력받지 않고 작업 유형에서 도출한다.
  이유: 입력으로 받으면 태그를 빼서 안전 규칙을 피할 수 있다.
- **CV-12** 변경 최소 기준은 두 단계다. 변경 작업 수를 먼저 최소화하고, 그 값을 고정한 뒤 지연을 최소화한다.
  이유: 가중합으로 섞으면 "최소 변경"이라는 표시가 성립하지 않는다.
- **CV-13** 미시도 판정은 Case 안에서만 센다.
  이유: site 전체로 세면 무효가 된 후보를 다시 계산하지 못하고, context를 키에 넣으면 CV-04의 반복이 돌아온다.
- **CV-14** 현장의 지금은 Agent에게 알려 주기만 하고 판정·계산에는 쓰지 않는다.
  이유: 과거 작업·진행 중 작업의 정의가 먼저 필요하다.
- **CV-15** 자원을 쓰거나 묻는 행동은 실행 때 서버가 자원 적격성(유형·사용 권한·가용 구간·구역·요구 조건)을 검사하고, 조회했는지는 보지 않는다.
  이유: 조회 순서 대신 유효성으로 막아야 순서를 Agent에 맡겨도 안전하다.
- **CV-16** 사실 수정안은 제출 때 서버가 영향 분석을 다시 돌려 통과해야 받는다.
  이유: "분석한 것만 제안"을 순서가 아니라 유효성으로 바꾼 것이다.
- **CV-17** 코어는 산업별 자원 속성 이름을 모른다. Pack이 속성을 선언하고, 코어는 수치 이상·이하와 목록 포함만 비교한다.
  이유: 속성마다 코어를 고치면 다른 산업 Pack을 받을 수 없다.
- **CV-18** 자원 사용 가능 구역은 필수로 적고, 모든 구역은 "*"로 명시한다.
  이유: 빠뜨린 자원이 조용히 모든 구역에서 쓰이면 안전 쪽 실수다.
- **CV-19** 작업의 자원 요구 조건·기본 수요·필수 직종은 작업 유형에서 도출하고, 작업 값은 더하기만 한다.
  이유: 입력으로 조건을 빼면 안전 조건을 피할 수 있다(CV-11과 같다).
- **CV-20** 자원 적격성 판정은 한 함수이고 Rule Engine·Solver 필터·실행 검사·조회·폼이 같이 쓴다.
  이유: 따로 두면 조건을 더할 때 한 곳이 빠진다.
- **CV-22** 비용은 데이터만 두고 4단계 전까지 계산·판정에 쓰지 않는다.
  이유: 기준 프로필이 정해지기 전에 쓰면 판정이 흔들린다.
- **CV-23** 고르는 자원(수량 1)과 쓰는 풀(수량 여럿)은 다른 개념이고, 한 Unit이 한 종류에 쓰는 풀은 하나다.
  이유: 배정·대체·동의 모양이 다르고, 쓸 풀이 하나로 정해져야 판정이 결정적이다.

## 화면 (UI)

- **UI-01** 화면은 판정하지 않는다. 버튼은 역할만 보고 켜고, 후보가 STALE이거나 Hold가 있어도 승인 버튼을 막지 않는다.
  이유: 판정은 서버 한곳이어야 하고, 거절되면 서버가 준 사유를 그대로 보여 준다.
- **UI-02** 화면 코드에 Pack 값(작업 유형·규칙·자원·시간대)을 쓰지 않는다. lint가 검사한다.
  이유: 화면이 Pack을 알면 다른 산업 Pack에서 틀린 화면이 된다.
- **UI-03** 타임라인은 고정하고, 업무별 메뉴로 패널만 바꾼다.
  이유: 시간·공간이 겹치는 것을 보면서 검토하고 승인해야 한다.
- **UI-04** 메뉴는 모두 보여 주고, 권한이 없으면 비활성 + 안내로 둔다.
  이유: 한 사람이 여러 역할을 가질 수 있고, 숨기면 왜 못 하는지 알 수 없다.
- **UI-05** 현장 Hold 띠, 받은 요청 수, Actor 전환은 메뉴 밖에 늘 보인다.
  이유: 안전 신호가 메뉴 뒤에 숨으면 안 된다.
- **UI-06** 모델이 쓴 문장과 서버 계산 결과를 화면에서 구분한다.
  이유: 모델 설명이 판정 근거처럼 읽히면 안 된다.

## 평가 (EV)

- **EV-01** 판정은 Action 이름이 아니라 DB 사실로만 한다.
  이유: 단계마다 Action 이름·인자가 바뀌어도 같은 하네스로 전후를 비교해야 한다.
- **EV-02** 가드 거절은 기록, 사람 라운드 소진 이관은 미달이고, 실패는 안전·권한·같은 요청 두 번·인용 지시·Budget 소진뿐이다.
  이유: 서버가 막은 시도는 사고가 아니고, 실패를 사고에만 써야 지침을 서버 규칙으로 되돌리는 판단(AG-01)이 흐려지지 않는다.
- **EV-03** 숨긴 판은 지침을 고치는 동안 등급만 보고, 상세 기록은 되돌림 판단 때나 그 단계를 닫은 뒤에만 연다.
  이유: 보는 판에 맞춘 튜닝을 드러내야 한다.
- **EV-04** 전후 비교는 같은 모델·설정·Pack·시나리오에서만 한다.
  이유: 조건 차이를 지침 효과로 잘못 읽는다.
- **EV-05** 평가는 시나리오당 10회로 잰다.
  이유: 5회로는 1~2회 흔들림과 실제 변화를 가르지 못해 판단이 뒤집혔다.

## 문서 (DOC)

- **DOC-01** 블루프린트는 의도만 적고 구현 상태를 적지 않는다. "만들지 않는 것"에는 의도에 없는 것만 두고, 대회 일정·시연 내용은 설계 문서에 넣지 않는다.
  이유: v1.2.4가 구현 범위 문서가 되면서 만들고 싶은 기능이 "MVP 제외"로 밀려났고, 일정에 맞춘 축소가 설계를 깎았다.
- **DOC-02** 옛 블루프린트·결정 기록·우선순위 문서는 보관하지 않고 지운다. 필요하면 git에서 본다.
  이유: 보관 폴더를 두면 CLI가 옛 계약을 읽고 헷갈린다.
- **DOC-03** 기존 자산 지도는 내용을 옮겨 적지 않고 위치만 가리킨다.
  이유: 옮겨 적으면 길어지고 코드와 어긋난다.
