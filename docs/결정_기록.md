# SAFE-ORCH 결정 기록

2026-10-05. 되돌려질 위험이 있는 결정만 적는다. 다른 선택지가 그럴듯했고, 이유를 모르면 누군가 "고치려" 할 결정이다.

- 항목 하나 = 결정 한 줄 + 이유 한 줄. 코드·SQL·함수 이름은 쓰지 않는다.
- 구현 기록("~를 구현했다")은 커밋 메시지에 둔다.
- 결정이 바뀌면 그 항목을 고쳐 쓰고, 무의미해지면 지운다. 옛 내용은 git에 있다. 지운 번호는 다시 쓰지 않는다.
- 200줄을 넘기지 않는다. 넘으면 비슷한 항목을 합친다.
- 단계를 닫을 때마다 한 번 정리한다(합치기·무의미해진 항목 지우기).

## Agent (AG)

- **AG-01** 순서 규칙("무엇을 한 뒤에만 무엇")은 서버가 아니라 스킬 지침에 둔다. 서버는 권한·안전·담당자 확인·인자 유효성·Budget만 강제한다.
  이유: 서버가 순서를 쥐면 매 step 선택지가 "다음 하나 vs 이관"뿐이라 Agent가 스크립트가 된다. 지침이 지켜지지 않으면 지침 문구·관찰 사실·도구 모양으로 고치고, 서버 순서 규칙으로 되돌리지 않는다. 서버에 남는 흐름 규칙은 같은 사실의 같은 호출·계산 금지(AG-24, CV-13), 답한 변경은 다시 묻지 않기(ST-15), 하위 Run은 한 번에 하나(ST-18), 보지 않은 사건·남은 일이 있으면 끝내지 않기뿐이다.
- **AG-02** 스킬은 행동마다 선언하고(켜 둔 상태를 저장하지 않는다) 사실 조건으로만 열리며, 쓸 수 있는 도구는 열린 스킬의 도구 ∩ Agent 허용 도구다. 유효한 인자 값이 하나도 없는 도구는 뺀다(순서가 아니라 유효성).
  이유: 켜 둔 상태 방식은 스킬만 바꾸는 step이 생겨 Budget이 실제 행동만 세지 못하고, 순서 조건을 두면 AG-01의 문제가 스킬 이름으로 다시 생기며, 여러 Agent가 공유하는 스킬이 Agent 권한을 넓히면 안 된다(예: Replanning은 사람 도구를 쓰지 못한다).
- **AG-05** Agent 호출은 Coordinator가 하위 Run을 만들고 부른 쪽은 대기·재개하는 방식으로 한다. LangGraph subgraph로 직접 부르지 않는다.
  이유: checkpointer 없이는 하위 Agent가 사람 답을 기다리는 동안 상위 그래프 상태를 보존할 수 없다.
- **AG-06** 전문 Agent는 다른 Agent를 부르지 않고 사람에게 이관하지도 않는다. 막히면 결과(상태·요약·풀 수 있는 길)를 돌려주고, 누구에게 넘길지는 메인이 판단한다. 전문 Agent는 어떤 끝에서도 이관 상태가 되지 않는다(서버가 끝내는 형식·전송 오류 2회도 막힘이다). Intake는 메인이 부르지 않는 입구라, 완료가 아닌 종료는 요청자에게 접수 미완으로 알린다.
  이유: 호출이 거미줄이 되면 핑퐁·순환을 막기 어렵고 판단이 흩어진다. Intake를 메인 아래 두면 요청자와 대화하는 동안 현장 전체가 멈추고, 작업이 아직 없어 메인이 할 일도 없다.
- **AG-07** 메인은 한 번에 하나이고 일이 남아 있는 동안만 산다. 사건이 생겼는데 열린 메인이 없으면 메인이 뜨고, 열린 메인은 하위 Run이 끝날 때나 하위 Run이 없을 때 사건이 생기면 깨어난다(하위 Run이 사람을 기다리는 동안에는 깨우지 않는다). 신고는 전문 Agent Run만 무효로 만들고 메인과 Intake Run은 남긴다(작성 중인 접수 값은 아직 사실이 아니고 완료할 때 다시 검증한다). 메인이 스스로 끝내지 못하면(Budget 소진·오류) 그 Case의 남은 일은 다음 메인에 넘기지 않고 Supervisor에게 알린다(대기 중인 작업은 대기열에 있어 잃지 않는다. 사건 합침은 3단계에서 정한다). 열린 메인이 있는 동안 온 접수(폼·자연어·일정의 새 작업)는 대기열에 서고, 메인이 끝나면 대기 중인 접수를 전부 한 번에 올린다(현장 버전 한 번, 사건은 접수마다 하나).
  이유: 사건마다 메인을 띄우면 겹친 사건의 순서를 판단할 곳이 없고, 상주 메인은 관찰·Budget이 끝없이 쌓이며 하나가 죽으면 현장이 멈춘다. 남은 일을 넘기면 소진 → 새 메인 → 소진이 이어질 수 있고, 남은 충돌은 다음 메인이 이전 결과와 함께 관찰로 본다. 대기열을 1건씩 올리면 일정 하나의 작업이 Case마다 흩어지고, 여러 충돌을 한 번에 푸는 재계획(AG-24)이 쓰이지 않는다.
- **AG-09** 작업 담당자 확인은 Coordination 한 창구로만 하고, Supervisor가 고른 안의 협의에서만 묻는다(후보 없이 미리 묻지 않는다). Agent는 그 밖의 사람에게 되묻지 않는다: Intake는 요청자에게(AG-32), Event Response는 신고자에게 묻지 않고 스스로 해석해 사실 수정안을 내거나 결과에 적는다. Agent가 낸 사실 수정안을 사람이 확인하는 것은 그대로다(사람 권한).
  이유: 여러 Agent가 같은 담당자에게 따로 묻는 것을 막는다. 미리 물으면 채택되지 않을 값까지 사람에게 묻게 된다(AG-34). 되묻기는 판단을 사람에게 되돌리고, 답이 안 온 항목을 같은 질문으로 반복했다. 사람에게 가는 것은 고른 안의 담당자 확인과 사람 권한뿐이다.
- **AG-10** AI는 일정·점수·중요도를 직접 계산하지 않는다. 설명과 추천은 서버 지표를 가리킨다.
  이유: 재현·검증이 안 되고, 모델에 따라 결과가 달라진다.
- **AG-11** Agent 지침 원문은 코드에 두고 바뀌면 prompt 버전을 올리며(fingerprint 테스트), 모델에 준 관찰과 AgentStep에 저장하는 관찰은 같다.
  이유: 모델이 실제로 받은 문장과 본 관찰이 기록과 같아야 AgentStep에 남은 버전으로 판단을 재현한다.
- **AG-13** 모든 Action은 실행 직전에 관찰 이후 버전이 바뀌었는지 확인하고, 바뀌었으면 실행하지 않는다.
  이유: 옛 관찰로 고른 행동을 새 사실 위에서 실행하지 않는다. "해가 없다"는 이관도 사실 판단이다.
- **AG-14** 제안(사실 수정)을 낸 Agent는 사람이 확인할 때까지 Run을 끝내지 않는다.
  이유: Run이 끝나면 그 Run이 보낸 요청이 정리되어 제안이 무효가 된다.
- **AG-17** LLM 전송 재시도는 SDK에 맡기지 않고 직접 1회 하며 시도 수를 Budget에 센다. 크레딧 부족은 재시도하지 않고 설정 오류로 끝낸다.
  이유: SDK 안의 재시도는 밖에서 보이지 않아 Budget에 셀 수 없다. 크레딧 부족은 기다려도 풀리지 않는다.
- **AG-19** 열리지 않은 스킬이나 스킬 밖 도구를 고른 행동은 거절하되 형식 오류 연속에 세지 않는다.
  이유: 스킬 선택 실수는 판단 실수라 Run을 끝낼 사유가 아니고 가드 거절로 기록된다.
- **AG-21** Agent 도구의 시각 인자는 현장 날짜·시각 문자열이고 서버가 분으로 바꾼다.
  이유: 모델이 날짜를 분으로 바꾸다 틀리고(셋째 날을 둘째 날로), AI는 일정을 계산하지 않는다(AG-10).
- **AG-23** 막힌 결과는 풀 수 있는 길 여러 개로 낸다(길마다 필요한 것의 묶음, 길이 없어도 된다). 필요한 것의 종류와 참조는 서버 목록이고(사실 변경, 사람의 답, 사람의 판단), Budget 소진은 종류가 아니라 종료 사유다. 서버는 열 수 있는 것을 사실로 계산해 Agent에게 주고 막힌 결과에도 붙이되 길로 엮지는 않는다. 필요한 것마다 서버가 ID를 붙이고, Agent가 엮은 길과 서버가 붙인 것을 구분해 남긴다.
  이유: 필요한 것 하나가 메인 행동 하나에 붙으면 메인이 라우터가 되고, 자유 문장은 지시가 된다. Budget이 종류에 있으면 같은 Agent를 다시 불러 새 Budget으로 우회한다. 길을 서버가 엮으면 판단이 서버로 가고, Agent가 길을 비우면 메인이 볼 것이 없다.
- **AG-24** 메인은 전문 Agent를 부를 때 Agent 종류와 참조만 넘기고, 하위 Run은 한 번에 하나만 연다. 재계획에는 접근만 넘긴다(AG-28): 재계획은 주체 Unit 없이 현장의 지금 충돌 전체를 한 번에 풀고, 범위 단계(충돌에 걸린 작업 → 같은 구역·같은 기준 자원의 작업 → 작업 전체)는 Unit을 가리지 않는다. 고정되지 않은 작업은 누구 작업이든 움직일 수 있고, 충돌 그룹은 호출 단위가 아니라 엮인 충돌의 설명이다. 메인 자신의 Unit은 권한 판정에 쓰지 않는다. 같은 Agent를 같은 참조(재계획은 같은 접근)로 다시 부를 때, 앞 Run(현장 전체의 마지막 Run)이 끝난 뒤 관련 사실(현장 버전, 그 후보의 승인·거절, 받은 답, 제안 상태, 보낸 통지, Hold)이 하나도 바뀌지 않았으면 거절한다.
  이유: 자유 문장 지시는 권한이 되고(안전 원칙 10), 하위 Run이 여럿이면 끊기·합치기 판단이 생긴다. 주체 Unit의 작업만 움직이면 두 Unit의 작업을 같이 옮겨야 풀리는 충돌에 해가 없고, Solver와 Validator는 전체 계획을 보므로 충돌 그룹 하나만 푸는 탐색은 다른 그룹의 충돌 때문에 해가 없다. 남의 작업을 담당자 확인 없이 바꾸지 않는 것(안전 원칙 8)은 협의 항목과 승인 조건이 지키므로 Unit 범위는 서버가 막을 경계가 아니다. 재호출 거절은 막힌 Agent를 새 Run의 Budget으로 우회하는 것과 다음 메인이 같은 시도를 되풀이하는 것을 막는다(순서가 아니라 사실 조건이다).
- **AG-25** Replanning은 후보 검증까지만 살고, 승인·거절 결과는 사건으로 메인이 받는다. 거절 뒤 다시 재계획할지 이관할지는 메인이 판단한다(거절 횟수로 서버가 끝내지 않는다). 사람의 결정을 기다리는 것과 확정 뒤 통지도 메인의 도구로 하고, 기다리기는 기다릴 것(검토 대기 후보, 걸린 Hold)이 있을 때만 유효하다.
  이유: 하위 Run이 하나라 재계획이 열려 있으면 협의를 부를 수 없다. 횟수로 끝내는 것은 서버 순서 규칙이다(AG-01). 서버가 재우거나 스스로 Agent를 부르면 무엇을 먼저 할지, 언제 부를지를 서버가 정하게 된다.
- **AG-27** 작업 고정·고정 해제는 사람만 타임라인에서 한다(담당자는 자기 작업, Supervisor는 모든 작업, Supervisor가 건 고정은 Supervisor만 푼다). Agent에게는 고정 도구가 없고 담당자의 이견은 결과에 담아 돌려준다. 확정된 작업이라고 고정으로 보지 않으며, 고정되지 않은 작업은 움직일 수 있다. 담당자 확인으로 고정을 우회하지 않고, 고정된 작업은 철회·없애기도 먼저 고정을 풀어야 한다.
  이유: 거절에서 자동으로 생긴 고정은 풀 길이 없었고, 무엇이 왜 묶였는지 화면에서 보이지 않았다. 확정을 고정으로 보면 다음 요청이 움직일 곳이 없어 재계획이 막힌다.
- **AG-28** 메인은 재계획을 접근을 달리해 순서대로 부른다. 접근은 정해진 목록(변경 최소·덜 옮기기)의 값 하나와 짧은 문장이고, 무엇을 우선할지만 정한다. 방식(범위 탐색, 조건 걸기, 직접 배치, 목적 순서)은 재계획이 고른다. 접근은 호출 키에 들어가고, 문장은 인용으로만 전해져 권한·인자 검사에 쓰지 않는다.
  이유: 방식만 다르면 같은 배치가 나와 사람이 비교할 안이 되지 않는다. 자유 문장만 넘기면 지시가 권한이 되고(AG-24), 같은 접근의 되풀이를 서버가 구분할 수 없다. 덜 옮기기는 기준에서 옮긴 거리(지연, CV-29)를 먼저 줄이는 것이다: 희망 영역을 없애면서 접근의 이름도 지연 쪽으로 바꿨다.
- **AG-29** Supervisor가 검토 대기 안 가운데 하나를 고르고, 메인은 고른 안만 협의로 보낸다. 고르는 것은 승인이 아니고(계획·현장 버전은 그대로), 고르지 않은 안은 그대로 두며, 고른 안을 바꾸면 앞 안의 열린 협의를 정리한다. 검토 대기 계산과 승인 조건은 바뀌지 않는다. Supervisor는 이 Case의 살아 있는 안을 사유 한 번으로 모두 거절할 수도 있다: 안마다 하나씩 거절과 같은 처리(결정 기록, 보낸 협의 요청 정리)이고, 사유는 한 번만 쌓이며(CV-26) 메인에게는 사건 하나다. 안 번호는 후보마다가 아니라 재계획 호출마다 하나이고(한 호출의 여러 안은 가·나, 다른 호출이 같은 배치를 내면 번호를 합친다) Case 안에서 바뀌지 않는다.
  이유: 안마다 먼저 협의하면 담당자가 채택되지 않을 안에도 답해야 하고, 같은 변경을 여러 번 묻게 된다. 나머지를 자동으로 거절하면 고른 안에 이견이 났을 때 돌아갈 안이 없다. 안마다 따로 거절하면 같은 사유가 안 수만큼 쌓이고 메인이 그만큼 깨어난다. 후보마다 번호를 매기면 어느 접근이 낸 안인지, 같은 호출이 낸 안인지가 번호에서 보이지 않는다.
- **AG-30** 메인의 step·전문 Agent 호출 한도는 그 Case에서 사람이 새 일을 만든 만큼(막힌 안 하나 = Supervisor 거절이나 담당자 이견이고 모두 거절은 안이 여럿이어도 하나, 작업 고정·고정 해제·직접 이동·없애기·카드에서 값 고치기, 고른 안을 바꿈) 한 바퀴분씩 상한까지 늘고, Agent 자신의 행동(재호출, 가드 거절, 재계획 결과)으로는 늘지 않는다. 한도는 저장하지 않고 사건·기록에서 계산한다.
  이유: 한도가 고정이면 사람이 판을 바꿀수록 메인이 일을 남긴 채 소진되고, Agent 행동으로도 늘면 Budget이 헛걸음을 묶지 못한다. 저장하면 사건 기록과 어긋날 수 있다(ST-05).
- **AG-31** 담당자는 자기 작업의 시각을 직접 옮기거나, 작업 카드에서 자원을 바꾸거나, 자기 작업을 없애고 Supervisor 승인 없이 확정한다(승인 규칙의 예외: 자기 작업 하나, 시각만 또는 자원만 바꾸거나 그 작업만 빼기, 검증 통과, ACTIVE Hold 없음). 카드의 자원 바꾸기는 직접 이동과 같은 판정이고, 확정하면 요청 자원도 새 자원이 된다. 사람이 만든 후보와 검증을 남기고, 현재 계획의 작업만 담으며(계획 밖 요청은 넣지 않고, 없앨 때는 요청 철회로 한다), 옮긴 작업을 고정하지 않는다. 없앤 작업은 지우지 않고 취소됨으로 남기며, 고정된 작업과 뒤에 이어지는 작업이 있는 작업은 없애지 못한다. Supervisor는 남의 작업을 옮기거나 없애지 못한다. 열린 Case 중에도 허용하고 고정·해제와 같은 방식으로 다루며(열린 메인에만 사건), 엮인 작업의 담당자에게는 서버가 통지한다.
  이유: 자기 작업만 바뀌어 확인할 다른 사람이 없고, 후보와 검증을 남겨야 누가 무엇을 옮겼는지가 다른 확정과 같은 모양으로 남는다. Supervisor가 옮기면 담당자 확인이 없다. 계획 밖 요청까지 담으면 충돌한 채 계획에 들어가고, 자동으로 고정하면 다음 재계획이 움직일 곳이 줄어든다(AG-27). 작업을 지우면 그 작업을 가리키는 불변 기록(후보·협의·통지)이 끊긴다.
- **AG-32** Intake는 요청자에게 묻지 않는다. 문장에 없는 값은 스스로 정해(작업 시간 추정, 조회한 적격 자원에서 고르기) 바로 완료하고, 값마다 사람이 말한 값인지 정한 값인지를 Agent가 적는다. 서버는 출처를 검사하지 않고, 정한 값만 화면에 따로 표시한다. 기록의 상태는 확인됨 그대로라 검증 규칙은 바뀌지 않는다. 문장의 시각은 시간창이 아니라 기준 위치(요청한 시작 범위)가 된다(AG-35·CV-29).
  이유: 모델 표시에 기댄 질문 제한은 우회됐다(모든 값을 받음으로 적고도 모호로 바꿔 물었다). 서버가 출처를 문장과 대조하면 해석이 서버로 간다. 틀린 값은 미리 묻는 대신 사람이 카드에서 보고 고친다. 추정한 작업 시간은 입력 값이지 일정 계산이 아니다(AG-10).
- **AG-33** 정한 값은 사람만 고친다. 요청자가 작업 카드에서 고치면 말한 값이 된다(현장 버전을 올리고 열린 Run을 깨운다). 그대로 확인하는 버튼은 두지 않는다. 계획에 아직 없는 자기 작업의 요청 시작 범위(기준 위치)도 카드에서 고치고, 고친 범위는 말한 범위가 된다(기준이 없는 폼 작업은 고칠 범위가 없고, 계획 작업의 기준은 승인된 자리라 직접 이동으로 옮긴다). 묻지 않는 범위(동의 기록·희망 영역)를 따로 두지 않는다: 고른 안의 협의에서 묻는 것은 기준에서 바뀐 작업이고, 협의 항목은 Solver의 변경 정의(CV-29)와 같은 기준으로 만든다. 새 작업은 기준 범위 밖으로 놓였거나 기준 자원이 아닐 때만, 기준이 없으면 자원이 바뀔 때만 항목이 된다. 재계획은 정한 값을 바꾸지 않고 열 수 있는 것으로 올린다. 계획에 있는 작업도 지금 배치가 깨지는 값으로 고칠 수 있다: 막지 않고, 고친 뒤 충돌이 있거나 계획 밖 요청이 남으면 작업 준비됨처럼 사건을 전해(열린 메인이 없으면 메인이 뜬다) Agent가 다시 푼다. 그렇지 않으면 열린 메인에만 전한다.
  이유: 동의 기록과 희망 영역은 둘 다 "묻지 않는 범위"를 들고 있는 같은 장치였고, 카드 확인은 그 동의를 만들려고 있던 것이다. 묻는 기준과 Solver의 변경 기준이 다르면 변경이 0인 안이 담당자에게 가거나 변경인 안이 묻지 않고 지나간다. 재계획이 값을 바꾸면 조건이 Hard를 넓힌다(CV-24). 배치가 깨지는 수정을 막으면 담당자가 틀린 값을 고칠 길이 없애고 다시 요청하기뿐이고, 받기만 하고 열린 메인에만 알리면 그 충돌을 처리할 주체가 없다.
- **AG-34** 고정되지 않은 작업은 시각도 자원도 움직인다. 작업마다 자원 축을 따로 여닫지 않고, 범위 안 고정되지 않은 작업은 서버가 적격성 함수로 채운 적격 자원 전체에서 Solver가 고른다(변경 수는 작업당 하나). 요청 자원은 Hard가 아니라 기준 자원이다: 그 자원이면 변경이 아니고, 다른 자원으로 바뀐 안은 고른 안의 협의에서 담당자에게 간다(CV-29). Agent에게 대체 자원을 여는 도구는 없고, 조건의 자원 지정(좁히기)만 있다.
  이유: 자원을 Agent가 열어야 하면 열어 보지 않은 채 해 없음으로 끝나거나, 여는 데 사람 질문이 필요했다. 자원을 못 박으려면 고정이 이미 있고, 요청 자원을 Hard로 두면 변경 최소 목적이 할 일을 사람이 미리 막는다.
- **AG-35** Hard는 사람이 구조화된 입력으로 직접 넣은 것만이다: 고정, 폼의 시간창, 작업 카드에서 고친 시간창. 자연어 요청에서 읽은 시간(말함이든 정함이든)은 기준 위치(요청한 시작 범위)가 되고 그 작업의 시간창은 Horizon 전체로 둔다(근무 시간 밖은 근무 달력이 막는다). 서버는 기준 밖으로 옮기는 안을 막지 않는다. 일정 문서의 시각은 구조화 입력이어도 Soft다: 문서의 배정이 기준 위치가 되고 시간창은 Horizon 전체이며, 문서의 고정은 살리지 않는다(ST-24). 가능 범위와 요청 시작 범위는 카드의 값 고치기로 담당자만 고친다(AG-33).
  이유: 자연어 "9시에서 10시 사이 시작"이 Hard 시간창이 되어, 다른 작업의 고정 하나로 요청 작업이 한 자리에서 움직이지 못했다. 문장에서 읽은 범위에는 Agent의 해석이 섞여 완화 금지 조건으로 삼을 근거가 약하다. Hard가 필요하면 고정과 시간창이 있다.

## 저장소·실행 (ST)

- **ST-01** 업무 상태와 Agent 실행 상태의 기준은 SQLite 하나다. LangGraph checkpointer·interrupt를 쓰지 않는다.
  이유: 실행 상태를 따로 두면 두 저장소의 정합 규칙이 필요하다. 매 step 최신 상태를 다시 관찰하므로 같은 Run을 처음부터 다시 호출하면 된다.
- **ST-02** 트랜잭션은 중첩하지 않고 하위 함수에는 트랜잭션을 인자로 넘기며, 트랜잭션 안에서 LLM·Solver·파일 I/O·await를 하지 않는다.
  이유: 중첩하면 커밋·롤백 범위가 흐려져 부분 반영이 생기고, 쓰기 트랜잭션이 곧 site 잠금이라 오래 잡으면 모든 명령이 기다리다 timeout난다.
- **ST-04** 거절된 명령은 handler의 쓰기를 모두 되돌린 뒤 결과 기록만 남긴다.
  이유: "거절이면 도메인 변화 없음"을 코드 습관이 아니라 구조로 보장한다.
- **ST-05** 후보·검증·협의의 상태(STALE, 표시 상태)는 저장하지 않고 조회할 때 계산한다. 메시지 취소와 제안 무효만 저장한다.
  이유: 불변 기록과 표시가 어긋나지 않는다. 늦은 답 기록과 받은 요청 화면에는 확정된 상태가 필요하다.
- **ST-07** 불변 기록(스냅샷·탐색 조건·Solver 결과·후보·검증·결정·감사)은 DB 트리거로 수정·삭제를 막는다.
  이유: 판단 근거가 나중에 바뀌면 감사 증거가 되지 못한다.
- **ST-08** 스키마 마이그레이션, 자동 초기화, 빈 DB 자동 seed를 하지 않는다. 버전이 다르면 기동을 멈추고, 초기화는 확인 문구를 거친 reset으로만 한다.
  이유: 자동 초기화는 Hold·Plan 기록을 조용히 지운다.
- **ST-09** 같은 멱등 키는 같은 명령·본문에만 저장된 결과를 돌려준다. 잠금 timeout만 결과를 저장하지 않는다.
  이유: 응답을 못 받은 재시도가 효과를 두 번 내지 않게 하고, 다른 요청이 같은 키로 옛 결과를 받지 않게 한다.
- **ST-10** 작성 중인 자연어 접수 값은 작업이 아니라 Run 기록에 둔다. 작업은 접수가 완료될 때 처음 생긴다.
  이유: 미완성 값이 스냅샷·충돌·버전에 영향을 주면 안 된다.
- **ST-11** 버전은 site 하나가 아니라 범위(작업·자원·구역)별로 둔다. 후보는 자기가 건드리는 범위가 바뀔 때만 무효가 된다. 그룹을 확정할 때는 그 변경만 현재 계획에 합치고 합친 전체를 다시 검증한다.
  이유: site 하나면 엮이지 않은 그룹의 확정이 다른 그룹의 후보·협의·사람 답을 모두 무효로 만든다. 일정 기능에서는 후보를 변경분으로 두고 승인 때 현재 계획에 합쳐 전체를 다시 검증하는 것까지 넣는다. 범위별 무효 판정은 미루고(그때까지 site 하나), 수동 테스트에서 검토 중인 안이 자주 깨지면 넣는다. 전체를 다시 검증해야 엮임 계산이 연결 하나를 놓쳐도 낡은 사실 위의 후보가 통과하지 않는다.
- **ST-13** 첫 구현에서는 ACTIVE Hold가 하나라도 있으면 모든 승인을 막는다.
  이유: 관련 없는 Hold를 무시하는 것은 안전 판단 완화라 따로 근거가 있어야 한다.
- **ST-15** 후보가 있는 협의에서 담당자 답은 후보가 아니라 변경(작업 revision·전후 배정)에 묶고, 현장 사실로 기록하지 않는다. 취소된 요청에 온 늦은 답은 같은 변경이 다시 나와도 인정하지 않는다.
  이유: 답을 현장 사실로 남기면 Context가 올라 방금 답받은 후보가 무효가 된다. 거둬들인 요청의 답을 살리면 Hold 중 결정을 허용하는 셈이다.
- **ST-17** 현장의 지금은 서버 한곳에서 읽고 Agent에게 알려 주기만 한다(판정·계산에는 쓰지 않는다). 테스트는 .env를 읽지 않고, 현장의 지금과 기준 설정(외부 모델 끔, 사건 → 메인 자동 시작 끔)을 한곳에서 고정한다.
  이유: 실제 시계와 개발자 .env는 결정론을 깬다(.env 때문에 테스트 46개가 실패한 적이 있다). 지금을 판정에 쓰려면 과거 작업·진행 중 작업의 정의가 먼저 필요하다.
- **ST-18** 열린 메인은 현장에 하나, 열린 하위 Run은 부모에 하나를 DB 유일성으로 지킨다.
  이유: 사건이 거의 동시에 오면 코드 검사만으로는 메인이 둘 뜬다.
- **ST-19** Agent 행동으로 Run이 끝날 때는 마지막 step 기록과 같은 트랜잭션에서 끝낸다. 기동 때 실행 중이던 Run은 예약만 된 step을 정리하고 관찰부터 다시 부른다.
  이유: 둘이 갈라지면 그 사이에 죽었을 때 재기동 뒤 같은 행동이 두 번 남는다. 매 step 최신 상태를 다시 관찰하므로 이어 가는 데 따로 저장할 상태가 없다(ST-01).
- **ST-20** 서버가 끝낸 하위 Run(무효·오류·Budget 소진·취소·시작 거절)의 결과는 서버가 Run 상태에서 만든다. 끝난 Agent를 다시 깨워 결과를 쓰게 하지 않는다.
  이유: 판단 없는 LLM 호출이 늘고, 깨운 모델이 결과 대신 다른 행동을 할 수 있다.
- **ST-21** 서버 계산 job(검증·협의 항목·재확인)을 Agent job보다 먼저 처리한다.
  이유: Agent는 검증·협의 항목·재확인이 끝난 사실을 관찰해야 한다.
- **ST-22** 고정은 작업 revision과 따로 기록하고(누가·언제), 계산에 들어가는 사실이다: Snapshot에 들어가고, 바뀌면 현장 버전을 올리고 열린 재계획·협의 Run을 깨우며, 열린 메인이 있을 때만 사건이 된다.
  이유: revision에 두면 켜고 끌 때마다 담당자 답이 초기화된다. 버전을 올려야 바뀐 사실 위의 후보가 기존 무효 판정으로 걸러진다. 고정만으로 새 Case를 열 일은 없다.
- **ST-23** 일정 문서는 불변 테이블에 정규화 JSON 원문으로 남기고 버전 번호를 매기지 않는다. 같은 일정인지는 머리말을 뺀 본문(작업·배정)의 hash와 꺼낸 시점의 계획 revision으로 가린다. 꺼내기는 현장 사실을 바꾸지 않지만 기록을 남기므로 조회가 아니라 명령이다(멱등 키).
  이유: 넣은 문서는 누가 무엇을 넣었는지의 근거라 나중에 바뀌면 안 되고, 파일로 두면 트랜잭션 안 파일 I/O가 된다(ST-02). 머리말(ID·시각)이 hash에 들어가면 같은 일정을 다시 꺼낼 때마다 다른 일정으로 보인다. 조회로 만들면 기록이 없어 넣은 문서가 어느 꺼내기에서 왔는지 댈 수 없다.
- **ST-24** 일정 넣기: 넣는 사람은 자기 Unit의 작업만 넣고, 새 작업의 담당자는 넣는 사람이며 넣은 값은 말한 값이다(문서의 출처는 쓰지 않는다). 새 작업의 기준 위치는 문서의 배정(시작·자원) 한 점이다(CV-29). 같은 ID의 자기 작업은 값이 다르면 작업 카드에서 고친 것과 같은 처리이고, 배정이 지금 계획과 달라도 쓰지 않는다(미리보기에 보이기만 한다. 문서대로 옮기는 길은 합치기 방향에서 정한다). 꺼낸 문서에 희망 영역 칸은 없고, 옛 문서에 있으면 받으면 버리고 미리보기에 표시한다. 넣기 판정은 새 작업 / 바뀌는 것 없음 / 값이 바뀜 / 넣을 수 없음이다. 넣을 수 없는 작업이 하나라도 있으면 전체를 거절하고, 사람이 미리보기에서 빼기로 고른 작업만 뺀다. 넣기 하나는 사건 하나다(대기열에서 오를 때도 일정 단위다).
  이유: 남의 작업을 넣으면 담당자가 말하지 않은 값이 말한 값이 된다(AG-33). 배정이 다르다고 계획 작업을 옮기면 승인된 자리가 승인 없이 바뀌고, 조용히 무시하면 무엇이 쓰이지 않았는지 사람이 모른다. 조용히 빼면 무엇이 들어가지 않았는지 사람이 모르고, 작업마다 사건을 내면 메인이 한 일정에서 온 작업임을 모른다.

## 계산·검증 (CV)

- **CV-01** Validator는 Solver 코드를 쓰지 않는다(Rule Engine은 같이 쓴다). 모르는 규칙은 무시하지 않고 실패로 본다.
  이유: 같은 코드로 만들고 검사하면 같은 버그를 못 잡는다. Pack과 코드가 어긋난 무결성 문제를 조용히 통과시키지 않는다.
- **CV-03** Solver가 낸 후보가 규칙 검사에서 실패하면 Run을 오류로 멈춘다(입력 미확인만 걸리면 계속).
  이유: 모델과 검증이 어긋난 것이라 계속하면 같은 오류를 반복한다.
- **CV-04** 탐색에는 무결성 해시(스냅샷 포함)와 실효 탐색 키(Solver 입력만) 두 가지를 둔다. "이미 해 본 탐색"은 실효 탐색 키로 판정한다. 실효 탐색 키에는 Solver 입력이 모두 들어간다(구역·속성·요구 조건·풀·수요·기준 시작 범위 포함). 고정은 키에 직접 넣지 않고 탐색 축을 통해서만 반영한다.
  이유: 버전 번호·확인 기록처럼 Solver 입력이 아닌 변화 때문에 같은 탐색이 새것처럼 보여 반복됐다. 고정을 직접 넣었더니 범위 밖 작업의 고정 때문에 같은 탐색이 다시 열렸다.
- **CV-06** Solver Budget은 돌리기 전에 차감하고, 결과가 버려져도 돌려주지 않는다.
  이유: 결과를 모르는 호출도 사용한 것으로 센다. 돌려주면 STALE이 반복될 때 Budget 상한이 의미를 잃는다.
- **CV-07** CP-SAT는 worker 하나, 고정 seed로 돈다.
  이유: 같은 입력이면 같은 답이어야 재현·검증과 "이미 해 본 탐색" 결과 반환이 성립한다.
- **CV-08** Pack에는 자원 겹침(CAPACITY) 규칙이 정확히 하나 있어야 한다.
  이유: Solver는 Pack과 관계없이 자원 겹침을 막으므로 Validator 기준을 맞춘다. 없으면 겹치는 후보가 통과할 수 있었다.
- **CV-09** 선행 작업이 없는 작업은 건너뛰지 않고 막는다. 후속 요청이 있는 작업은 후속부터 철회해야 한다.
  이유: 조용히 건너뛰면 선후행을 어긴 계획이 통과한다.
- **CV-10** 근무 달력은 기본 제약이고 자원 가용 구간과 따로 둔다.
  이유: 장비 가용과 현장 근무는 다른 사실이고, 합치면 야간 배치가 두 번 보고된다.
- **CV-11** 위험 태그와 작업의 자원 요구 조건·기본 수요·필수 직종은 입력받지 않고 작업 유형에서 도출한다. 작업 값은 조건을 더하기만 한다.
  이유: 입력으로 받으면 태그나 조건을 빼서 안전 규칙을 피할 수 있다.
- **CV-12** 변경 최소 기준은 단계 순서다. 변경 작업 수를 먼저 최소화하고, 그 값을 고정한 뒤 지연을 최소화하고, 마지막으로 둘을 고정한 채 자원을 바꾸는 작업 수를 최소화한다(변경 수는 작업당 하나라, 시각을 바꾼 작업의 자원을 더 바꿔도 앞의 두 값이 같다). 목적 순서가 지연 먼저여도 마지막 단계는 같다(CV-27).
  이유: 가중합으로 섞으면 "최소 변경"이라는 표시가 성립하지 않는다.
- **CV-13** 미시도 판정은 Case 안에서만 센다. 무효가 되었고(현장 버전이 달라짐) 거절·확정되지 않은 후보의 탐색은 미시도로 보고 실제로 다시 계산한다. 거절된 후보의 탐색과 후보가 없는 결과(해 없음·미확정)는 해 본 탐색으로 남는다. 해 본 탐색(같은 사실·범위·조건·목적 순서)을 다시 부르면 Solver를 돌리지 않고 Budget도 쓰지 않으며, 그때의 결과를 도구 결과로 돌려준다(앞 Run이 한 것도 같다).
  이유: site 전체로 세면 무효가 된 후보를 다시 계산하지 못하고, context를 키에 넣으면 CV-04의 반복이 돌아온다. 거절된 후보의 탐색을 다시 열면 같은 배정이 또 나온다. 사유 코드만 돌려주면 모델이 같은 호출을 조건이 다르다고 믿고 되풀이해 step Budget을 소진했다.
- **CV-16** 사실 수정안은 제출 때 서버가 영향 분석을 다시 돌려 통과해야 받는다.
  이유: "분석한 것만 제안"을 순서가 아니라 유효성으로 바꾼 것이다.
- **CV-17** 코어는 산업별 자원 속성 이름을 모른다. Pack이 속성을 선언하고, 코어는 수치 이상·이하와 목록 포함만 비교한다.
  이유: 속성마다 코어를 고치면 다른 산업 Pack을 받을 수 없다.
- **CV-18** 자원 사용 가능 구역은 필수로 적고, 모든 구역은 "*"로 명시한다.
  이유: 빠뜨린 자원이 조용히 모든 구역에서 쓰이면 안전 쪽 실수다.
- **CV-20** 자원 적격성(유형·사용 권한·가용 구간·구역·요구 조건) 판정은 한 함수이고 Rule Engine·Solver 필터·실행 검사·조회·폼이 같이 쓴다. 자원을 쓰는 행동은 실행 때 이 함수로 검사하고, 먼저 조회했는지는 보지 않는다. 사용 권한은 그 작업의 Unit으로 판정한다(재계획에 주체 Unit은 없다, AG-24).
  이유: 따로 두면 조건을 더할 때 한 곳이 빠진다. 조회 순서 대신 유효성으로 막아야 순서를 Agent에 맡겨도 안전하다.
- **CV-22** 비용은 데이터만 두고 4단계 전까지 계산·판정에 쓰지 않는다.
  이유: 기준 프로필이 정해지기 전에 쓰면 판정이 흔들린다.
- **CV-23** 고르는 자원(수량 1)과 쓰는 풀(수량 여럿)은 다른 개념이고, 한 Unit이 한 종류에 쓰는 풀은 하나다.
  이유: 배정·대체·협의 모양이 다르고, 쓸 풀이 하나로 정해져야 판정이 결정적이다.
- **CV-24** Agent가 탐색에 거는 조건(작업별 시작 범위·시작 지정·자원 지정)은 좁히기만 한다. 서버는 유효성(시각 형식, 시간창 안, 고정 아님, 범위 안 작업, 자원 적격)만 보고, 조건은 탐색 기록에 남아 실효 탐색 키에 들어간다. 같은 범위·같은 조건은 다시 풀지 않고, 조건이 다르면 범위를 다 쓴 뒤에도 푼다.
  이유: 범위를 넓히는 것만으로는 사람이 말한 사유를 안에 담을 수 없어 재계획이 같은 답만 냈다. 조건이 Hard를 넓힐 수 있으면 Agent 판단이 안전 규칙을 완화한다(안전 원칙 2).
- **CV-25** 살아 있는 재계획 후보와 전체 배정이 같은 해는 새 후보로 만들지 않고, 그 시도가 기존 후보에 도달했다고 남긴다.
  이유: 범위만 다른 계산이 같은 배치를 후보 두 개로 올려, 하나가 거절된 뒤 같은 배치로 담당자에게 다시 물었다.
- **CV-27** 목적 순서(변경 작업 수 먼저 / 지연 먼저, 지연은 CV-29)는 Agent가 조건 도구로 고르는 입력이다. 탐색 기록에 남고 실효 탐색 키에 들어가며, 기본은 변경 먼저다(CV-12).
  이유: 지연을 우선하는 안은 가중합이 아니라 단계 순서를 바꿔야 "기준에서 가장 덜 옮김"이라는 표시가 성립한다. 서버가 접근에서 목적을 정하면 방식 선택이 서버로 간다(AG-28).
- **CV-26** 사람이 남긴 사유(Supervisor 거절 문장, 담당자 이견)는 Case가 닫힐 때까지 재계획 관찰에 전부 쌓이고, 서버는 사유를 해석하지 않는다. 서버가 하는 것은 살아 있는 후보가 거절·이견된 변경과 같은 변경을 담았는지의 표시뿐이며 그 후보를 같이 거절하지 않는다. 담당자 이견은 재계획 호출의 사실 지문에 들어간다. Supervisor가 안을 모두 거절한 사유는 안이 여럿이어도 한 번만 쌓인다(AG-29).
  이유: 서버가 문장을 조건으로 바꾸면 판단이 서버로 가고 틀린 해석이 Hard가 된다. 마지막 사유만 보이면 앞 사유를 어긴 안이 다시 나온다. 이견이 지문에 없으면 이견 뒤의 재계획 재호출이 막힌다.
- **CV-28** 직접 이동에서 놓을 수 있는 시작 구간은 서버가 계산한다(현재 계획에서 그 작업만 바꾼 배치를 Validator로 본다). 화면은 받은 구간을 칠하기만 하고, 놓을 때와 확정할 때 서버가 같은 판정을 다시 한다.
  이유: 화면이 규칙을 따로 계산하면 서버 판정과 어긋나고 Pack을 알게 된다(UI-01·UI-02). 구간을 받은 뒤 사실이 바뀔 수 있어 확정 때의 판정이 기준이다.
- **CV-29** 변경과 지연은 작업의 기준 위치 하나에서 잰다. 계획 작업의 기준은 승인된 자리(한 점)라 옮기면 변경이고 옮긴 거리(앞뒤 모두)가 지연이다. 새 작업의 기준은 요청한 시작 범위다: 일정은 문서의 배정(한 점), 자연어는 문장에서 말한 시작 범위이고(접수 Agent가 정한 범위도 똑같이 쓴다. "몇 시까지 끝"은 서버가 시작 한도 = 종료 한도 − 작업 시간으로 바꾼다), 범위 안이면 변경 0·지연 0, 밖이면 변경 1·범위 끝에서 벗어난 거리다. 폼처럼 요청 시각이 없는 새 작업은 기준이 없어 시간창 안 어디든 변경 0·지연 0이다(가장 이른 시작을 자리처럼 쓰지 않는다). 새 작업의 자원은 기준 자원(일정은 문서 배정의 자원, 그 밖에는 요청 자원)이 아니면 변경이다. Solver 목적, 조회, 근무 분 지연, 화면 숫자, 협의 항목(AG-33)이 같은 정의다.
  이유: 희망 영역을 지연의 기준으로 두고 사람이 그리고 Agent가 만들고 조건으로 Hard처럼 걸게 했더니 Soft가 사실상 제약이 되어, 재계획이 희망 영역을 거의 벗어나지 않았다. Hard가 필요하면 고정과 시간창이 있다(AG-35). 가장 이른 시작 기준의 지연 최소는 작업을 Horizon 앞으로 당기고, 늦어진 만큼만 세면 앞당기는 것이 공짜라 계획 작업을 하루 앞으로 당기는 해가 나왔다. 기준이 없는 작업에 기준을 만들어 넣지 않는다: 아직 자기 자리가 없으므로 재지 않는다.

## 화면 (UI)

- **UI-01** 화면은 판정하지 않는다. 버튼은 역할만 보고 켜고, 후보가 STALE이거나 Hold가 있어도 승인 버튼을 막지 않는다.
  이유: 판정은 서버 한곳이어야 하고, 거절되면 서버가 준 사유를 그대로 보여 준다.
- **UI-02** 화면 코드에 Pack 값(작업 유형·규칙·자원·시간대)을 쓰지 않는다. lint가 검사한다.
  이유: 화면이 Pack을 알면 다른 산업 Pack에서 틀린 화면이 된다.
- **UI-03** 타임라인은 고정하고, 업무별 메뉴로 패널만 바꾼다. 현장 Hold 띠, 받은 요청 수, Actor 전환은 메뉴 밖에 늘 보인다.
  이유: 시간·공간이 겹치는 것을 보면서 검토하고 승인해야 하고, 안전 신호가 메뉴 뒤에 숨으면 안 된다.
- **UI-04** 메뉴는 모두 보여 주고, 권한이 없으면 비활성 + 안내로 둔다.
  이유: 한 사람이 여러 역할을 가질 수 있고, 숨기면 왜 못 하는지 알 수 없다.
- **UI-06** 모델이 쓴 문장과 서버 계산 결과를 화면에서 구분한다.
  이유: 모델 설명이 판정 근거처럼 읽히면 안 된다.
- **UI-07** 기준이 범위인 새 작업의 기준은 타임라인에 작업 막대 모양으로 그리지 않는다. 작업을 선택했을 때만 요청 시작 범위를 가능 범위와 구분되는 괄호로 보이고, 안을 겹쳐 볼 때는 새 배치 라벨에 "기준 범위 안"이나 범위 밖으로 옮긴 분과 방향을 적는다. 기준이 한 점인 작업(계획 작업, 일정의 새 작업)은 변경 전 윤곽을 쓴다.
  이유: 범위에 작업 시간을 더해 막대로 그리면 작업이 그만큼 길어 보이고, 요청한 자리처럼 읽힌다.

## 평가 (EV)

- **EV-06** 평가 하네스·live run·골든 테스트를 두지 않는다. CLI의 확인은 pytest·ruff까지이고, Agent 동작은 사용자가 화면에서 직접 본다.
  이유: 판정 기준과 고정된 흐름에 맞추느라 서버 규칙이 늘고, 구현마다 수치 맞추기만 반복해 기능이 늘지 않았다.

## 문서 (DOC)

- **DOC-01** 블루프린트는 의도만 적고 구현 상태를 적지 않는다. "만들지 않는 것"에는 의도에 없는 것만 두고, 대회 일정·시연 내용은 설계 문서에 넣지 않는다. 옛 문서는 보관하지 않고 지우며(git에서 본다), 기존 자산 지도는 내용을 옮겨 적지 않고 위치만 가리킨다.
  이유: v1.2.4가 구현 범위 문서가 되면서 만들고 싶은 기능이 "MVP 제외"로 밀려났고, 일정에 맞춘 축소가 설계를 깎았다. 보관 폴더를 두면 CLI가 옛 계약을 읽고 헷갈리고, 옮겨 적으면 길어지고 코드와 어긋난다.
