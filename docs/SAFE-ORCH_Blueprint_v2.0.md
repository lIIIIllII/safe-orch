# SAFE-ORCH Blueprint v2.0

Safety-Constrained Agentic Orchestration System · 2026-10-05

무엇을 왜 만드는가를 적는 문서다. 무엇이 구현됐는지는 코드와 `기존_자산_지도.md`가 보여 준다. 코드·SQL·함수 이름은 쓰지 않는다.

> LLM may propose. Solver may optimize. Safety Kernel must validate. Human must authorize.

## 1. 정의와 문제

**한 줄 정의.** 여러 작업 주체가 공간·장비·시간을 함께 쓰는 현장에서, 새 작업이나 현장 변경이 만든 안전 규칙·자원 충돌을 AI Agent들이 조사·계산·확인해 검증된 작업계획 변경안을 만들고, 사람이 고르고 승인한다.

**문제.**
- 계획은 주체(원청·협력사)별로 따로 세우지만, 계획 사이의 겹침(인양 아래 작업, 화기 옆 도장, 장비 이중 배정)은 사람이 전화·회의·엑셀로 조정한다.
- 그래서 충돌을 늦게 발견하고, 조정안이 경험에 의존하며, 현장이 바뀌어도 이미 승인된 계획이 그대로 쓰일 위험이 있다.
- 요청자는 자기 작업을 고정하려는 경향이 있어 "옮길 수 있나요?" 같은 추상적인 질문은 거절되기 쉽고, 후보 → 거절 → 재탐색이 반복된다.
- 자연어로 말한 조건("10시 30분에 시작해야 해")이 그대로 절대 조건이 되어 해를 막는다.

**범용성.** 코어는 작업·작업 주체(Unit)·자원·구역·구역 관계·안전 규칙만 안다. 산업별 차이(작업 유형, 위험 태그, 규칙 수치, 근무 달력, 표시 이름)는 Domain Pack으로 표현한다. 조선소 원·하청 혼재작업은 예시 Pack 하나일 뿐이다.

## 2. 목표와 원칙

- 계산은 서버의 정해진 규칙(Rule Engine·Solver·Validator)이, 판단은 AI Agent가, 선택과 승인은 사람이 한다.
- AI는 일정·점수·중요도를 직접 계산하지 않는다. 계산은 서버에 맡기고, 서버가 준 사실과 지표를 근거로 판단하고 설명한다.
- 서버는 경계만 맡는다: 사람의 권한, 지정된 사람의 답만 효력이 있다는 것, 안전 검사, 계산, Budget. 무엇을 어떤 순서로 할지는 Agent가 판단하고, 안을 하나가 아니라 여러 개 낸다. 서버는 선택지를 미리 좁히거나 순서를 정하지 않는다.
- 사람은 안을 고르고 승인한다. 그리고 타임라인에서 직접 고정·이동·없애기·값 고치기를 한다. Agent는 사람이 직접 바꾼 사실 위에서 다시 판단한다.
- Hard(완화 금지)는 안전 규칙과, 사람이 구조화된 입력으로 직접 넣은 것만이다. Agent가 읽거나 정한 값은 Hard가 되지 않는다.
- 효율 목표: Hard 조건을 지키면서 변경 작업 수 → 기준에서 옮긴 거리 → 사람에게 묻는 횟수 순으로 줄인다.
- Agent는 사람에게 되묻지 않는다. 판단은 Agent가 하고, 사람에게 가는 것은 고른 안의 담당자 확인과 사람 권한(승인, 사실 수정 확인)뿐이다. 확인을 요청할 때는 실제 값을 붙여 묶어서 보낸다.
- 후보는 하나씩 내지 않고 기준별로 여러 개를 한 번에 보여 주며, 사람이 고른다.
- 관찰 → 선택 → 재관찰을 반복하지 않는 구성요소는 Agent라고 부르지 않는다.

## 3. 사용자와 역할

| 역할 | 하는 일 |
|---|---|
| Unit Planner | 작업 요청(폼·자연어), 자기 요청 철회 |
| 작업 담당자 | 자기 작업의 변경 확인에 수락·거절·이견, 자기 작업의 시각을 타임라인에서 직접 옮기기, 자기 작업 없애기, 작업 카드에서 값과 요청 시작 범위 고치기 |
| 신고자 | 현장 변경(지연 등) 신고 |
| Supervisor | 후보 선택·승인·거절(하나씩 또는 살아 있는 안 모두), 협의 항목 수용, 사실 수정 확인, Hold 해제, Run 취소 |

작업을 요청한 사람이 그 작업의 담당자다. 역할과 담당 관계는 서버의 Actor 정보로만 판단한다.

## 4. 핵심 기능

**작업 등록**
- 폼(여러 작업을 한 묶음으로)과 자연어·작업계획 입력을 모두 받는다. 둘 다 "확인된 작업 묶음"이 되고, 그 뒤 흐름은 입력 방식을 모른다. 여러 작업을 한 번에 넣는 입구는 일정 넣기다(아래 일정).
- 폼 값은 사람이 말한 값이다. 자연어에서는 Intake Agent가 요청자에게 되묻지 않고 작업을 만든다: 문장에 없거나 해석·추정이 들어간 값은 Agent가 정하고, 정한 값만 화면에 따로 표시한다. 요청자는 작업 카드에서 그 값을 고치고, 고친 값은 말한 값이 된다.
- 상대 날짜(내일·오전)는 현장의 지금 기준으로 푼다. 요청한 시각은 그 작업의 기준 위치가 된다: 한 시각으로 말했으면 한 점, 범위로 말했으면 그 시작 범위다. 폼처럼 요청 시각이 없으면 기준 위치가 없다.
- 위험 태그는 입력받지 않고 작업 유형에서 서버가 도출한다. 해결되지 않은 요청은 요청자가 철회할 수 있다.
- 자원은 사용 가능 구역과 Pack이 선언한 속성을 갖는다. 작업의 자원 요구 조건은 작업 유형 기본값에 요청 값이 더해진 것이고, 자원이 그 조건과 맞는지는 서버가 판정한다.
- 인력 같은 수량 자원은 풀로 두고, 작업 유형이 기본 수요와 필수 직종을 정한다. 겹치는 작업의 수요 합이 풀 수량을 넘으면 충돌이다.

**조건: Hard와 Soft**
- 요청 조건을 Hard(절대 마감·안전 규칙, 완화 금지)와 Soft(기준 위치: 벗어난 거리를 줄인다)로 나누고, 자연어에서 온 조건은 출처를 남긴다.
- Hard는 사람이 구조화된 입력으로 직접 넣은 것만이다: 작업 고정, 요청 폼의 시간창(가능 범위), 작업 카드에서 고친 시간창. 자연어 요청에서 읽은 시간은 가능 범위가 아니라 기준 위치가 되고, 그 작업의 가능 범위는 계획 기간 전체다.
- 고른 안이 작업을 기준에서 바꾸면 실제 값을 붙여 그 담당자에게 확인을 요청한다. 수락·이견 모두 정상 경로다. 이견은 사유와 함께 재계획으로 돌아가고, 작업을 묶지는 않는다(묶으려면 사람이 고정한다).
- 담당자가 답한 변경은 같은 변경이 다시 나와도 다시 묻지 않는다. 그 작업이 바뀌었을 때만 다시 묻는다.
- 사람은 타임라인에서 작업을 고정하고 푼다(담당자는 자기 작업, Supervisor는 모든 작업). 고정된 작업은 재계획이 움직이지 않고, 고정되지 않은 작업은 확정된 계획에 있어도 움직일 수 있다.
- 작업마다 기준 위치가 하나다. 계획 작업은 승인된 자리(한 점), 새 작업은 요청한 자리(일정은 문서의 배정 한 점, 자연어는 문장에서 말한 시작 범위)이고, 폼처럼 요청 시각이 없으면 기준이 없다. 기준은 Soft다: 서버가 강제하지 않지만 계산의 기준이다. 변경과 지연은 기준에서 잰다: 범위 안이면 변경도 지연도 아니고, 밖이면 변경이며 범위 끝에서 벗어난 거리(앞뒤 모두)가 지연이다. 기준이 없는 새 작업은 가능 범위 안 어디든 변경이 아니다. 묻지 않는 범위를 따로 두지 않는다: 고른 안의 협의에서 묻는 것은 기준에서 바뀐 작업이다.
- 가능 범위와 요청 시작 범위는 담당자만 작업 카드에서 고친다(요청 시작 범위는 계획에 아직 없는 작업만). 둘 다 타임라인에서 작업을 선택했을 때 서로 다른 모양의 괄호로 보인다. 기준 위치는 작업 카드에 글로 보이고, 안을 겹쳐 볼 때 기준이 한 점인 작업은 변경 전 자리의 윤곽으로, 기준이 범위인 새 작업은 새 배치에 범위 안·밖을 적어 보인다.
- 안을 볼 때는 그 안의 기준 계획을 확정한 뒤 사람이 바꾼 사실(고친 값, 고친 요청 시작 범위, 고정·해제, 없앤 작업)을 함께 보인다. 배치가 그대로인 재확정에도 무엇 때문에 다시 확정하는지 보인다.

**충돌 탐지와 묶음 나누기**
- 서버가 안전 규칙·자원·시간창·근무 달력 위반을 탐지한다.
- 묶음 안의 작업을 엮임(선후행, 같은 자원, 같은 구역의 가까운 시간)으로 그룹 짓는다. 엮임 계산은 서버가 한다.
- 그룹은 엮인 충돌을 설명하는 단위다. 재계획은 그룹을 가리지 않고 현장의 지금 충돌 전체를 한 번에 푼다.

**재계획과 복수 후보**
- 무엇을 우선할지는 접근 목록에서 고른다. 접근이 목적 순서를 정하고, Solver는 그 순서대로 사전식으로 줄인다(가중합으로 섞지 않는다): 바뀌는 작업 수, 기준에서 옮긴 거리, 자원을 바꾸는 작업 수. 접근 목록은 Case 종류로 나뉜다: 일정이 아닌 Case는 변경 최소·덜 옮기기, 일정 Case는 세 방향이다.
- 재계획은 작업 주체를 가리지 않는다. 고정되지 않은 작업은 누구 작업이든 움직일 수 있고, 다른 사람의 작업이 바뀐 안은 고른 뒤 협의에서 그 담당자의 확인을 받아야 승인된다.
- Replanning Agent는 메인이 준 접근으로 후보를 만들고(목적 순서는 접근이 정한다), 필요하면 조건을 걸어 다른 해를 찾는다. 안의 차이는 서버가 계산한 숫자로 보이고 고르기는 사람이 한다(Agent의 비교·추천은 만들지 않는다, §10).
- 같은 탐색을 다시 요청하면 계산하지 않고 이전 결과를 돌려준다. 원인 진단·완화 시험 같은 알아보기 도구는 만들지 않는다(§10): 재계획은 계산 결과와 조건으로 움직인다.
- 사람이 후보 하나를 고르면 그 후보만 협의한다. 승인과 협의 항목 수용도 고른 후보에만 되고(재확인 후보도 고른 뒤 승인한다), 다른 안으로 가려면 그 안을 고른다. 고르지 않은 후보는 그대로 남아, 고른 후보에 이견이 나면 돌아갈 수 있다. 어느 안도 받을 수 없으면 사유를 한 번 적어 살아 있는 안을 모두 거절하고, 그 사유는 재계획으로 돌아간다. 안 번호는 재계획 결과가 나온 순서대로 매기고, 같은 배치를 낸 결과의 번호는 이어 보인다. 해가 없으면 이유와 필요한 것을 붙여 이관한다.

**협의와 통지**
- Coordination Agent가 작업 담당자 확인의 단일 창구다. 변경 요청은 담당자 한 명에게 한 통이고 그 담당자의 항목을 전부 담는다(항목은 서버가 채우고 Agent는 고르지 않는다). 담당자는 항목마다 수락하거나 사유를 적어 이견을 내고, 한 통을 한 번에 답한다.
- 고정되지 않은 작업은 적격 자원 안에서 자원도 바뀔 수 있다. 요청 자원은 기준 자원이다: 그 자원이면 변경이 아니고, 다른 자원으로 바뀐 안은 Supervisor가 고른 뒤 협의에서 담당자에게 묻는다. 담당자는 작업 카드에서 자기 작업의 자원을 직접 바꿔 확정할 수도 있다.
- 담당자 이견은 결과에 담겨 메인 Agent에게 돌아가고 재계획으로 이어진다. Agent는 이견을 제약으로 바꾸지 않는다. Supervisor는 고른 안의 미확인 항목을 사유와 함께 수용할 수 있다.
- 고른 안이 무효가 되면(현장·계획이 바뀜, 거절, 다른 안을 고름) 그 협의는 서버가 바로 정리한다. 그 뒤에 온 답은 기록만 남고 답으로도 이견 사유로도 쓰이지 않는다. 이미 한 답은 그 변경에 묶여 남는다.
- 확정 뒤 관련 주체에게 시간·구역·위험·조치를 통지한다. 바뀌지 않았어도 안전 규칙으로 연결된 작업의 담당자에게 알린다.

**현장 변경 대응**
- 신고가 접수되는 순간 서버가 Hold를 건다. Agent의 지연·실패가 안전 차단을 늦추지 않는다.
- Event Response Agent가 대상 작업을 찾고, 영향을 분석하고, 사실 수정안을 만든다. 신고 내용이 모호해도 신고자에게 되묻지 않고 스스로 해석하며, 해석할 근거가 없으면 그 사유를 결과에 적는다. 사실 수정은 Supervisor 확인으로만 적용된다.
- Hold를 해제하면 다시 검사해 충돌이 있으면 재계획, 없으면 재확정 후보를 만든다.

**검증·승인·작업 시작 표시**
- 승인 조건: Supervisor가 고른 안 ∧ 검증 통과 ∧ 후보를 만든 뒤 현장 사실과 계획이 바뀌지 않음(현장 버전이 최신) ∧ ACTIVE Hold 없음 ∧ 협의 완료.
- 승인의 예외(직접 이동·자원 바꾸기·작업 없애기): 담당자가 자기 작업 하나의 시각만 옮기거나 자원만 바꾸거나 그 작업만 계획에서 빼는 것은 검증 통과 ∧ ACTIVE Hold 없음이면 Supervisor 승인 없이 확정된다. 없앤 작업은 취소됨으로 남는다. 놓을 수 있는 자리는 서버가 같은 규칙으로 계산해 보여 주고, 엮인 작업의 담당자에게 알린다.
- 후보는 계획 전체를 담고 전체 계획으로 검증한다. 확정하면 후보의 배정이 그대로 새 계획이 된다.
- 작업마다 시작 가능 여부(Gate)를 보여 준다. 확정 계획에 있고 관련 변화와 Hold가 없을 때만 시작 가능이다.

**일정**
- 일정은 계획 기간 하나의 작업과 배정 전체를 묶은 단위다. 반정형 문서(JSON)로 꺼내고 넣고, 이미 계획된 일정과 합친다. 같은 계획 기간 안의 일정만 다룬다.
- 새 일정을 짜지 않는다. 들어온 일정을 문서의 배정대로 기존 계획 위에 올려 전체를 검토하고, 충돌하는 부분만 정리한다. 충돌이 없으면 재확정 후보가 된다. 들어온 작업의 기준 위치는 문서의 배정이다.
- 문서의 시각은 Soft다. 문서의 배정이 새 작업의 기준 위치(한 점)가 되고 가능 범위는 계획 기간 전체다. Hard가 필요하면 넣은 뒤 작업 카드에서 고친다. 문서의 고정은 살리지 않는다. 문서에 희망 영역 칸은 없고, 옛 문서에 있으면 받으면 버리고 미리보기에 알린다.
- 넣는 사람은 자기 Unit의 작업만 넣는다. 새 작업의 담당자는 넣는 사람이고, 넣은 값은 담당자가 말한 값이다. 합칠 때 기존 계획의 확정 작업을 고정으로 보지 않는다.
- 일정 하나는 사건 하나다. 열린 메인이 있으면 대기열에 서고, 메인이 끝나면 대기 중인 접수를 한 번에 올린다.
- 일정에 충돌이 있으면 메인이 일정 검토 Agent를 부른다. 일정 검토 Agent는 서버가 계산한 충돌·최소 묶음(작업을 공유하는 충돌)·묶음 사이 관계를 보고 실제 묶음을 정하고 검토 의견을 낸다. 묶음은 최소 묶음의 합만이고(서버는 그것만 검사하고 묶음을 대신 정하지 않는다), 낸 묶음안은 그때의 사실에 묶인 불변 기록이다. 재계획은 묶음과 관계없이 현장 충돌 전체를 한 번에 풀고, 묶음안은 사람에게 보이는 설명과 이관 근거로 쓴다: 사람만 풀 수 있는 묶음(걸린 작업이 모두 고정된 것 등)은 표시해 두고 메인이 이관할 때 쓴다.
- 검토 의견은 안 비교 위에 서버 사실과 구분해 보인다.
- 합치기 방향은 기존 위주, 추가 위주, 적절하게 셋이다. 기존 위주는 기존 작업(지금 계획에 있는 작업)의 변경 수를 먼저 줄이고, 추가 위주는 추가 작업(계획에 없는 작업)의 변경 수를 먼저 줄여 들어온 작업을 문서 자리에 두며, 적절하게는 전체 변경 수를 줄인다. 방향은 조건이 아니라 목적이라 해의 유무를 바꾸지 않는다. 세 방향은 같은 범위(작업 전체)에서 풀고, 세 방향의 안을 모두 내 Supervisor가 안 비교에서 고른다. 안의 이름은 그 안을 낸 방향이고, 서버는 안마다 기존 작업 변경 수, 추가 작업 변경 수, 기준에서 옮긴 거리를 계산해 보인다. 최적이 확인되지 않은 안은 그렇게 표시한다.
- 넣을 수 없는 작업(남의 작업, 계획 기간 밖 시각, 없는 구역·자원, 빠진 값)이 하나라도 있으면 전체를 거절한다. 미리보기가 작업마다 판정과 사유를 보여 주고, 사람이 그 작업을 빼기로 고르면 나머지만 넣는다.
- 같은 작업 ID는 담당자 본인일 때 같은 작업으로 본다: 값이 다르면 작업 카드에서 고친 것과 같다. 배정이 지금 계획과 달라도 쓰지 않고 미리보기에 알리기만 한다(어느 방향에서도 쓰지 않는다. 옮기려면 담당자가 직접 이동한다). 꺼낸 문서를 그대로 넣으면 바뀌는 것이 없다. 기존 계획에만 있는 작업은 없애지 않는다. 취소·철회된 ID는 다시 쓰지 못한다.
- 빠진 값은 거절한다. 끝 − 시작처럼 계산으로 나오는 값만 서버가 채운다. 위험 태그는 받지 않는다. 일정은 폼·자연어 요청과 따로 둔 입구다.

## 5. Agent 구조 개요

- **메인 Agent**: 사건(작업 준비됨, 일정 넣기, 신고, Hold 해제, 안 고르기, 후보 승인·거절, 하위 Run 결과, 요청 철회, 사람이 타임라인·작업 카드에서 직접 바꾼 것)을 받아 어떤 전문 Agent를 어떤 순서·입력으로 부를지, 결과를 받아 다음에 무엇을 할지, 언제 기다리고 언제 멈출지 판단한다. 사람의 답은 사건이 아니라 물은 전문 Agent가 받는다.
- **전문 Agent**: Replanning(재계획·후보 구성), Coordination(협의·통지), Event Response(현장 변경), Schedule Review(일정의 충돌을 묶음으로 정리·검토 의견). 메인이 부른다.
- **Intake(접수)**는 메인이 부르지 않는 입구다. 요청 문장에서 시작해 묻지 않고 완료하며, 완료가 "작업 준비됨" 사건이 된다. 작업이 아직 없어 메인이 할 일이 없으므로 메인 밖에 둔다.
- 전문 Agent는 다른 Agent를 직접 부르지 않는다. 막히면 이유와 필요한 것을 결과에 담아 메인에게 돌려준다. 열 수 있는 것은 서버가 사실로 계산해 주고, 풀 수 있는 길은 전문 Agent가 엮고, 어느 길을 탈지는 메인이 고른다.
- 부르기는 Coordinator를 거친다. 메인이 요청을 남기면 Coordinator가 전문 Agent Run을 만들고, 메인은 대기했다가 결과로 재개한다. Coordinator는 전달·기록·대기와 재개·검증 실행만 하고, 누구를 부를지는 판단하지 않는다.
- 메인은 한 번에 하나이고 일이 남아 있는 동안만 산다. 열린 메인이 있으면 새 사건은 그 메인의 Case에 들어가고, 새 작업 접수는 대기열에 섰다가 메인이 끝나면 한 번에 올라간다.
- Budget은 두 층이다. 전문 Agent는 자기 Budget(step, LLM, Solver, 사람 확인)을, 메인은 자기 step과 전문 Agent 호출 수를 센다. 메인의 한도는 그 Case에서 사람이 새 일을 만든 만큼 상한까지 늘고, Agent 자신의 행동으로는 늘지 않는다.
- 사람에게 묻는 창구: 작업 담당자 확인은 Coordination만 하고, Supervisor가 고른 안의 협의에서만 한다. Intake와 Event Response는 사람에게 묻지 않는다.

**스킬 3층 구조**
- 아래층(서버, 항상): 권한·안전·담당자 확인·인자 유효성·Budget. 어떤 스킬을 켜도 바뀌지 않는다.
- 스킬 층(서버): 스킬마다 도구 묶음과 열리는 조건을 둔다. 열리는 조건은 할 일이 있는지 같은 사실 조건만이고 순서 조건은 두지 않는다. 실제로 쓸 수 있는 도구 = 스킬의 도구 ∩ 그 Agent에 허용된 도구.
- 지침(모델 판단): 순서와 요령. 지침 원문은 코드에 두고 버전으로 관리한다.
- Agent는 열린 스킬 중에서 고르고, 여러 스킬을 함께 쓰고, Run 도중 바꾼다. 행동마다 어떤 스킬로 하는지 밝히며, 스킬을 바꾸는 데 Budget을 쓰지 않는다.

**실행 계약.** 1 step = step 예약 → LLM 1회 → Action 1개. 모든 도구 실행은 Tool Gateway를 거친다. Agent·도구·스킬의 목록과 규칙은 `Agent_도구_스킬.md`에 있다.

## 6. 안전 원칙

1. Agent는 승인·확정·거절·Hold 해제·사실 수정 확정·협의 수용·작업 고정·고정 해제·직접 이동·작업 없애기·작업 값 고치기를 할 수 없다. 이 기능은 Agent 도구에 코드상 없다.
2. Hard 조건과 안전 규칙은 목적함수·선호·사람 피드백·Agent 판단으로 완화되지 않는다.
3. 모든 후보는 Solver와 독립된 Validator가 전체 계획으로 검사한다. 통과하지 않은 후보는 승인할 수 없다.
4. 현장 변경 신고는 접수 트랜잭션 안에서 Hold를 건다. 첫 구현에서는 ACTIVE Hold가 하나라도 있으면 모든 승인이 막힌다.
5. Hold는 하나씩 해제하며, 해제해도 옛 승인은 되살아나지 않는다.
6. 사람이 고정한 작업과 사람이 구조화된 입력으로 넣은 가능 범위는 이후 모든 탐색과 검증에서 Hard다. 거절과 이견은 작업을 묶지 않는다(같은 배정을 다시 제안하지 않을 뿐이다).
7. 사람의 답은 질문이 만들어진 시점의 작업 revision·값에 묶이고, 지정된 사람이 답할 때만 효력이 있다.
8. 작업 주체는 자원의 허용 목록에 있어야 그 자원을 쓸 수 있고, 다른 주체의 작업은 그 담당자 확인 없이 바꾸지 않는다.
9. 모든 상태 변경은 한 쓰기 트랜잭션 안에서 최신 상태를 다시 읽고 검사한 뒤 쓴다. 트랜잭션 안에서 LLM·Solver·사람 대기를 하지 않는다.
10. 프레임워크에 넘기는 값과 모델 출력은 권한이 아니다. 사람이 쓴 자유 텍스트는 인용 데이터로만 다룬다.
11. 같은 요청을 다시 보내도 효과는 한 번만 남는다.

PASS는 "현재 Pack 규칙 기준으로 정의된 위반이 없다"는 뜻이다. 현장 안전 보장이나 법규 판정이 아니다. "최적"은 그 탐색 범위 안에서의 최적이다.

## 7. 데이터와 버전 개념

- 작업은 revision으로 관리한다. 값을 바꾸면 새 revision을 만든다.
- 작업 조건 값마다 출처(폼, 자연어, 메시지)와 확인 상태(제안 / 확인)를 둔다. 확인되지 않은 값으로는 검증을 통과하지 못한다.
- 담당자의 답은 그 변경(작업 revision·전후 배정)에만 묶인다. 받은 답을 다른 자원이나 다른 시간으로 넓히지 않는다.
- 스냅샷·탐색 조건·Solver 결과·후보·검증 결과는 불변이다. 조건이 바뀌면 새로 만든다. 후보의 무효(STALE) 여부는 저장하지 않고 조회할 때 계산한다.
- 버전은 현장 하나다. 현장 사실이나 계획이 바뀌면 그 전에 만든 후보는 모두 무효가 된다.
- 업무 상태와 Agent 실행 상태의 기준은 SQLite 하나다. Agent 대기·재개도 DB 기록으로 한다.
- Domain Pack은 기동할 때 한 번 읽고 해시로 고정한다. Pack이 바뀌면 이전 기록과 섞이지 않는다.
- 현장의 지금은 서버 한곳에서 정하며, 시연·테스트에서는 고정할 수 있다.
- 테이블·컬럼은 `기존_자산_지도.md`가 가리키는 원본을 따른다.

## 8. 화면

- 한 화면에 상태바, 타임라인, Agent 활동, 입력 탭, 검토 패널이 함께 있다. 타임라인은 크게 볼 수 있다.
- 입력 탭: 작업 요청, 자연어 요청, 일정 넣기, 지연 신고, 받은 요청. 탭은 모두 보이고, 권한이 없으면 숨기지 않고 비활성 + 안내다.
- 검토 패널: 후보 목록, 일정 검토(묶음·의견), 안 비교, 고른 후보의 검증·협의·승인. Agent 활동: Run과 step마다 관찰·행동·결과.
- 언제나 보이는 것: 현장 Hold, 받은 요청 수, Actor 전환.
- 화면은 판정하지 않는다. 버튼은 역할만 보고 켜고, 승인 가능 여부는 서버가 판정해 사유를 보여 준다.
- 모델이 쓴 문장(이유·의견)과 서버 계산 결과를 화면에서 구분한다.
- 화면은 Pack을 모른다. 작업 유형·규칙 이름·시간대·근무 구간은 서버에서 받는다.

## 9. 기술 스택

- Backend: Python 3.12, FastAPI(sync endpoint), Pydantic
- 저장소: SQLite + 표준 sqlite3, ORM 없음
- Agent 실행: LangGraph(checkpointer·interrupt 없이), LangChain(모델 호출·도구 스키마)
- 계산: OR-Tools CP-SAT
- Frontend: React + TypeScript + Vite
- 개발 도구: uv, pytest, ruff, oxlint. 버전은 lock 파일이 기준이다.

## 10. 만들지 않는 것

- 실제 설비 제어나 작업 지시 실행
- 법규 판정, 현장 안전 보장 주장
- AI가 사람 대신 승인·확정하는 기능
- 원인 진단·완화 시험·미리보기·후보 비교 같은 알아보기 도구(신고 대응의 영향 분석은 있다)
- Agent가 안을 비교해 추천하는 기능(숫자는 서버가 보이고 고르기는 사람이 한다)
