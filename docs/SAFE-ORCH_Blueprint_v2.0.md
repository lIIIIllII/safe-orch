# SAFE-ORCH Blueprint v2.0

Safety-Constrained Agentic Orchestration System · 2026-10-03

무엇을 왜 만드는가를 적는 문서다. 무엇이 구현됐는지는 코드와 `기존_자산_지도.md`가 보여 준다. 코드·SQL·함수 이름은 쓰지 않는다.

> LLM may propose. Solver may optimize. Safety Kernel must validate. Human must authorize.

## 1. 정의와 문제

**한 줄 정의.** 여러 작업 주체가 공간·장비·시간을 함께 쓰는 현장에서, 새 작업이나 현장 변경이 만든 안전 규칙·자원 충돌을 AI Agent들이 조사·계산·확인해 검증된 작업계획 변경안을 만들고, 사람이 고르고 승인한다.

**문제.**
- 계획은 주체(원청·협력사)별로 따로 세우지만, 계획 사이의 겹침(인양 아래 작업, 화기 옆 도장, 장비 이중 배정)은 사람이 전화·회의·엑셀로 조정한다.
- 그래서 충돌을 늦게 발견하고, 조정안이 경험에 의존하며, 현장이 바뀌어도 이미 승인된 계획이 그대로 쓰일 위험이 있다.
- 요청자는 자기 작업을 고정하려는 경향이 있어 "옮길 수 있나요?" 같은 추상적인 질문은 거절되기 쉽고, 후보 → 거절 → 재탐색이 반복된다.
- 자연어로 말한 조건("10시 30분에 시작해야 해")이 그대로 절대 조건이 되어 해를 막는다.

**범용성.** 코어는 작업·작업 주체(Unit)·자원·구역·구역 관계·안전 규칙만 안다. 산업별 차이(작업 유형, 위험 태그, 규칙 수치, 근무 달력, 표시 이름)는 Domain Pack으로 표현한다. 조선소 원·하청 혼재작업은 예시 Pack 하나일 뿐이다.

## 2. 목표와 원칙

- 계산은 서버의 정해진 규칙(Rule Engine·Solver·Validator)이, 판단은 AI Agent가, 선택과 승인은 사람이 한다.
- AI는 일정·점수·중요도를 직접 계산하지 않는다. 서버가 연 선택지와 서버 지표 위에서 판단하고 설명한다.
- 흐름은 풀고 권한은 고정한다. Agent는 무엇을 어떤 순서로 할지 스스로 고르고, 권한·안전·동의는 서버가 강제한다.
- 효율 목표: Hard 조건을 지키면서 변경 작업 수 → 총 지연 → 사람에게 묻는 횟수 순으로 줄인다.
- 사람에게는 조회·계산으로 알 수 없는 것만 묻고, 물을 때는 실제 값을 붙여 묶어서 묻는다.
- 후보는 하나씩 내지 않고 기준별로 여러 개를 한 번에 보여 주며, 사람이 고른다.
- 관찰 → 선택 → 재관찰을 반복하지 않는 구성요소는 Agent라고 부르지 않는다.

## 3. 사용자와 역할

| 역할 | 하는 일 |
|---|---|
| Unit Planner | 작업 요청(폼·자연어), 자기 요청 철회 |
| 작업 담당자 | 자기 작업의 변경 확인에 수락·거절·이견 |
| 신고자 | 현장 변경(지연 등) 신고, 되묻기에 답 |
| Supervisor | 후보 선택·승인·거절, 협의 항목 수용, 사실 수정 확인, Hold 해제, Run 취소 |

작업을 요청한 사람이 그 작업의 담당자다. 역할과 담당 관계는 서버의 Actor 정보로만 판단한다.

## 4. 핵심 기능

**작업 등록**
- 폼(여러 작업을 한 묶음으로)과 자연어·작업계획 입력을 모두 받는다. 둘 다 "확인된 작업 묶음"이 되고, 그 뒤 흐름은 입력 방식을 모른다.
- 폼 값은 확인된 값이다. 자연어에서 Intake Agent가 뽑은 값은 제안 상태이며 요청자 확인을 받아야 확인된 값이 된다. 빠진 값은 묶어서 한 번에 묻는다.
- 위험 태그는 입력받지 않고 작업 유형에서 서버가 도출한다. 해결되지 않은 요청은 요청자가 철회할 수 있다.

**조건: Hard와 Soft**
- 요청 조건을 Hard(절대 마감·안전 규칙, 완화 금지)와 Soft(희망, 넘으면 벌점)로 나누고, 자연어에서 온 조건은 출처를 남긴다.
- 후보가 Soft 조건을 넘으면 실제 값을 붙여 담당자에게 묻는다. 수락·거절 모두 정상 경로이고, 거절되면 Hard가 된다.
- 거절된 값은 다시 묻지 않는다. 그 작업에 관련된 사실이 바뀌었을 때만 바뀐 내용을 붙여 다시 물을 수 있다.

**충돌 탐지와 묶음 나누기**
- 서버가 안전 규칙·자원·시간창·근무 달력 위반을 탐지한다.
- 묶음 안의 작업을 엮임(선후행, 같은 자원, 같은 구역의 가까운 시간)으로 그룹 짓는다. 엮임 계산은 서버가 한다.
- 엮이지 않은 그룹을 먼저 확정 단계로 보낼지, 충돌 그룹을 기다릴지는 메인 Agent가 판단한다. 요청자가 "한 세트"로 표시한 묶음은 나누지 않는다.

**재계획과 복수 후보**
- 서버에 작업 피처(인력·자원·시간·비용)와 기준별 가중치 프로필(비용 중심, 지연 중심, 변경 최소 등)을 둔다.
- Replanning Agent는 의미 있는 기준을 고르고, 후보를 만들고, 후보들이 실제로 다른지 점검하고, 확인이 필요한 조건을 찾고, 서버 지표로 차이를 설명·추천한다.
- 알아보기 도구(원인 진단, 완화 시험, 미리보기, 영향 분석, 후보 비교)로 "왜 안 풀리나, 무엇을 풀면 풀리나"를 근거 삼아 움직인다. 같은 탐색을 다시 요청하면 계산하지 않고 이전 결과를 돌려준다.
- 사람이 후보 하나를 고르면 그 후보만 협의하고 나머지는 무효가 된다. 해가 없으면 이유와 필요한 확인을 붙여 이관한다.

**협의와 통지**
- Coordination Agent가 작업 담당자 확인의 단일 창구다. 여러 그룹의 질문을 한 사람에게 묶어 보낸다.
- 담당자 이견은 담당자 확인을 거쳐 제약이 되고 재계획으로 이어진다. Supervisor는 미확인 항목을 사유와 함께 수용할 수 있다.
- 확정 뒤 관련 주체에게 시간·구역·위험·조치를 통지한다. 바뀌지 않았어도 안전 규칙으로 연결된 작업의 담당자에게 알린다.

**현장 변경 대응**
- 신고가 접수되는 순간 서버가 Hold를 건다. Agent의 지연·실패가 안전 차단을 늦추지 않는다.
- Event Response Agent가 대상 작업을 찾고, 영향을 분석하고, 필요하면 신고자에게 되묻고, 사실 수정안을 만든다. 사실 수정은 Supervisor 확인으로만 적용된다.
- Hold를 해제하면 다시 검사해 충돌이 있으면 재계획, 없으면 재확정 후보를 만든다.

**검증·승인·작업 시작 표시**
- 승인 조건: 검증 통과 ∧ 후보가 건드리는 범위의 버전이 최신 ∧ ACTIVE Hold 없음 ∧ 협의 완료.
- 확정할 때 그 그룹의 변경을 현재 계획에 합치고, 합친 전체 계획을 다시 검증한다.
- 작업마다 시작 가능 여부(Gate)를 보여 준다. 확정 계획에 있고 관련 변화와 Hold가 없을 때만 시작 가능이다.

**질의응답**
- Site Assistant가 "왜 내 작업이 밀렸나" 같은 질문에 근거 ID를 붙여 답한다. 읽기 전용이며, 근거가 없으면 모른다고 답한다.

## 5. Agent 구조 개요

- **메인 Agent**: 사건(작업 묶음, 신고, 거절, 답변)을 받아 어떤 전문 Agent를 어떤 순서·입력으로 부를지, 결과를 받아 다음에 무엇을 할지, 언제 멈출지 판단한다.
- **전문 Agent**: Intake(접수), Replanning(재계획·후보 구성), Coordination(협의·통지), Event Response(현장 변경), Site Assistant(질의응답, 읽기 전용).
- 전문 Agent는 다른 Agent를 직접 부르지 않는다. 막히면 이유와 필요한 것을 결과에 담아 메인에게 돌려준다.
- 부르기는 Coordinator를 거친다. 메인이 요청을 남기면 Coordinator가 전문 Agent Run을 만들고, 메인은 대기했다가 결과로 재개한다. Coordinator는 전달·기록·대기와 재개·검증 실행만 하고, 누구를 부를지는 판단하지 않는다.
- 메인은 한 번에 하나이고 일이 남아 있는 동안만 산다. 열린 메인이 있으면 새 사건은 그 메인을 깨우고, 메인이 지금 일에 합칠지 뒤로 미룰지 판단한다.
- Budget은 두 층이다. 전문 Agent는 자기 Budget(step, LLM, Solver, 알아보기 계산, 사람 확인)을, 메인은 자기 step과 전문 Agent 호출 수를 센다. 사건을 합치면 메인 Budget을 더하되 상한이 있고, 상한에 닿으면 새 사건을 받지 않고 지금 일만 정리한 뒤 남은 사건을 다음 메인에게 넘긴다.
- 사람에게 묻는 창구: 작업 담당자 확인은 Coordination만 한다. 요청자와의 접수 대화는 Intake가, 신고자 되묻기는 Event Response가 직접 한다.

**스킬 3층 구조**
- 아래층(서버, 항상): 권한·안전·동의·인자 유효성·Budget. 어떤 스킬을 켜도 바뀌지 않는다.
- 스킬 층(서버): 스킬마다 도구 묶음과 열리는 조건을 둔다. 열리는 조건은 할 일이 있는지 같은 사실 조건만이고 순서 조건은 두지 않는다. 실제로 쓸 수 있는 도구 = 스킬의 도구 ∩ 그 Agent에 허용된 도구.
- 지침(모델 판단): 순서와 요령. 지침 원문은 코드에 두고 버전으로 관리한다.
- Agent는 열린 스킬 중에서 고르고, 여러 스킬을 함께 쓰고, Run 도중 바꾼다. 행동마다 어떤 스킬로 하는지 밝히며, 스킬을 바꾸는 데 Budget을 쓰지 않는다.

**실행 계약.** 1 step = step 예약 → LLM 1회 → Action 1개. 모든 도구 실행은 Tool Gateway를 거친다. Agent·도구·스킬의 목록과 규칙은 `Agent_도구_스킬.md`에 있다.

## 6. 안전 원칙

1. Agent는 승인·확정·거절·Hold 해제·사실 수정 확정·협의 수용을 할 수 없다. 이 기능은 Agent 도구에 코드상 없다.
2. Hard 조건과 안전 규칙은 목적함수·선호·사람 피드백·Agent 판단으로 완화되지 않는다.
3. 모든 후보는 Solver와 독립된 Validator가 전체 계획으로 검사한다. 통과하지 않은 후보는 승인할 수 없다.
4. 현장 변경 신고는 접수 트랜잭션 안에서 Hold를 건다. 첫 구현에서는 ACTIVE Hold가 하나라도 있으면 모든 승인이 막힌다.
5. Hold는 하나씩 해제하며, 해제해도 옛 승인은 되살아나지 않는다.
6. 확인된 조건(사람이 거절하거나 고정한 것)은 이후 모든 탐색과 검증에서 Hard다.
7. 사람의 답은 질문이 만들어진 시점의 작업 revision·값에 묶이고, 지정된 사람이 답할 때만 효력이 있다.
8. 작업 주체는 자원의 허용 목록에 있어야 그 자원을 쓸 수 있고, 다른 주체의 작업은 그 담당자 확인 없이 바꾸지 않는다.
9. 모든 상태 변경은 한 쓰기 트랜잭션 안에서 최신 상태를 다시 읽고 검사한 뒤 쓴다. 트랜잭션 안에서 LLM·Solver·사람 대기를 하지 않는다.
10. 프레임워크에 넘기는 값과 모델 출력은 권한이 아니다. 사람이 쓴 자유 텍스트는 인용 데이터로만 다룬다.
11. 같은 요청을 다시 보내도 효과는 한 번만 남는다.

PASS는 "현재 Pack 규칙 기준으로 정의된 위반이 없다"는 뜻이다. 현장 안전 보장이나 법규 판정이 아니다. "최적"은 그 탐색 범위 안에서의 최적이다.

## 7. 데이터와 버전 개념

- 작업은 revision으로 관리한다. 값을 바꾸면 새 revision을 만든다.
- 작업 조건 값마다 출처(폼, 자연어, 메시지)와 확인 상태(제안 / 확인)를 둔다. 확인되지 않은 값으로는 검증을 통과하지 못한다.
- 사람의 동의는 작업·축·값 단위다. 받은 동의를 다른 자원이나 다른 시간으로 넓히지 않는다.
- 스냅샷·탐색 조건·Solver 결과·후보·검증 결과는 불변이다. 조건이 바뀌면 새로 만든다. 후보의 무효(STALE) 여부는 저장하지 않고 조회할 때 계산한다.
- 버전은 범위별로 둔다. 후보는 자기가 건드리는 작업·자원·구역의 버전이 바뀔 때만 무효가 된다.
- 업무 상태와 Agent 실행 상태의 기준은 SQLite 하나다. Agent 대기·재개도 DB 기록으로 한다.
- Domain Pack은 기동할 때 한 번 읽고 해시로 고정한다. Pack이 바뀌면 이전 기록과 섞이지 않는다.
- 테이블·컬럼은 `기존_자산_지도.md`가 가리키는 원본을 따른다.

## 8. 화면

- 타임라인을 고정하고, 왼쪽 사이드바의 업무별 메뉴로 옆 패널을 바꾼다.
- 메뉴: 현황, 작업 요청, 받은 요청, 후보 검토, 현장 신고·Hold, Agent 활동, 질문하기. Agent 활동과 질문하기는 패널을 넓게 펼칠 수 있다.
- 메뉴는 모두 보이고, 권한이 없으면 숨기지 않고 비활성 + 안내다. Actor 역할에 따라 처음 열리는 메뉴만 다르다.
- 어느 메뉴에서도 보이는 것: 현장 Hold 띠, 받은 요청 수, Actor 전환.
- 화면은 판정하지 않는다. 버튼은 역할만 보고 켜고, 승인 가능 여부는 서버가 판정해 사유를 보여 준다.
- 모델이 쓴 문장(설명·추천)과 서버 계산 결과를 화면에서 구분한다.
- 화면은 Pack을 모른다. 작업 유형·규칙 이름·시간대·근무 구간은 서버에서 받는다.

## 9. 기술 스택

- Backend: Python 3.12, FastAPI(sync endpoint), Pydantic
- 저장소: SQLite + 표준 sqlite3, ORM 없음
- Agent 실행: LangGraph(checkpointer·interrupt 없이), LangChain(모델 호출·도구 스키마)
- 계산: OR-Tools CP-SAT
- Frontend: React + TypeScript + Vite
- 개발 도구: uv, pytest, ruff, oxlint. 버전은 lock 파일이 기준이다.

## 10. 만들지 않는 것

- 실제 설비 제어나 작업 지시 실행
- 법규 판정, 현장 안전 보장 주장
- AI가 사람 대신 승인·확정하는 기능

## 11. 열린 질문

- 버전을 쪼갤 단위와 규칙(작업·자원·구역)
- 평가 지표: Agent가 "모든 기준 계산 + 중복 제거 + 템플릿 설명" 스크립트보다 나은지 무엇으로 볼지(후보: 사람 질문 수, 재탐색 횟수, 선택된 후보의 지표, 추천-선택 일치율). 시연값 밖 시나리오 필요
- 기준 프로필의 수와 정의, 가중치 계산 방식, Soft 벌점 단위
- "서로 다른 후보"의 기준, 프로필 수만큼 늘어나는 계산 시간
- 후보를 "보여 줘도 된다"는 판단을 Agent와 서버 중 어디에 둘지
- 추천이 사실상 결정이 되지 않게 하는 표시 방식
- 메인 Budget 상한, 사건을 합칠 때 더하는 양, 알아보기 계산 Budget
- 후보 여러 개를 타임라인에 겹쳐 보이는 방식, Agent 호출 흐름 그림
- 범용성 확인용 두 번째 Pack의 산업
- 프로세스가 죽었을 때 진행 중 Run을 이어 가는 방식
